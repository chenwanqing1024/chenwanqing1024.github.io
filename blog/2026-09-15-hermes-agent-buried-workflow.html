Hermes Agent 改造埋点流程：把 AI 边界画在”判断前”，人在判断后

2026-09-15 · Agent 数据研发 工作流编排 工程落地

读文笔记。本文是对他人文章的摘要与评述，非原文转载。 原文：从埋点需求到规则资产：Hermes Agent 重构得物数仓工作流 · 得物技术

原文在说什么

得物这篇讲的是数仓埋点需求承接的工程现实——最消耗数据承接方的是把分散的信息重新拼起来：需求文档里的动作到底要不要采集，历史上有没有类似点位，指标口径有没有被下游使用，新增字段要改哪几层表，发布前又该由谁确认。

作者选了 Hermes Agent 而不是 OpenClaw，因为 Hermes 有三个原生能力对得上这类流程痛点：持续在线、持久记忆、技能沉淀。

在 Hermes 之上，把一次埋点需求承接拆成四个可追踪工程构件：工作区（每个需求独立空间，集中存放需求文档、历史讨论、评审结论、交付产物）、看板（状态机流转：进入→设计→预演→评审→交付，每步有责任人）、规则 + 长期记忆（把”老同学才知道”的判断写成可执行检查清单）、结构化工具接口 + 预演 + 人工确认点（高风险动作走结构化接口，写入生产前先预演、再等人放行）。

核心判断：让 AI 直接给最终结论确实快，但这种快不让人放心——数仓链路里的错误通常是依据没找全、假设没说清、风险没暴露，最后带着”看起来完整”的方案进评审或生产。所以 Hermes Agent 的边界是把问题整理到足够可判断——它负责组织材料、历史、候选方案、系统预演和风险证据；人负责业务语义、指标口径、敏感字段、下游影响和生产放行。

选型思路：不把能力拆成一组互相独立的智能体（MultiAgent），而是选择”单 Agent 编排 + 多能力模块 + 看板确认点”。Hermes 保持统一上下文、负责调度阶段；能力模块承接稳定动作、负责把工具调用、输入约束、输出产物、停顿条件固化下来。

固化流程契约——每个能力模块的输入、动作边界、输出产物、失败处理、经验回写。只有这些契约稳定，Hermes 才不会因为提示词换一种说法就改变检查重点。

可复用能力模块——不是只服务一次埋点需求，而是把素材采集、历史检索、变更预演、发布确认、经验沉淀抽成可复用的流程模块。换事实源和工具接口后，同一套机制能迁移到指标发布、配置变更、数据质量排查。可复用的 SKILL 就是这套机制的核心载体。

端到端工作流示例（业务要”稳定查看昨天各体裁发布量”）：如果只让模型直接写 SQL，很容易把物理字段、业务发生日期、默认过滤混在一起——Hermes 的做法是先固化事实，再预演风险，最后把需要人判断的点推到看板确认。

我的看法

我认同作者把”AI 边界画在判断前”的判断。这篇文章给我最有价值的不是架构本身，而是几个反直觉的工程判断：

第一，单 Agent + 多能力模块 vs 多 Agent 编排是经典选择。文章选了前者，理由是同一类需求换个问法输出结构和检查重点就会漂；如果拆成多个独立智能体，统一上下文就丢了。多 Agent 适合异构任务（一个对话含多个领域），单 Agent + 模块化适合流程化任务（一类需求反复出现）。

第二，固化流程契约比写好 prompt 更重要。能力模块的输入、动作边界、输出产物、失败处理、经验回写——这五件事固化下来，prompt 怎么写都不会偏。这是软件工程里”契约优于配置”的范式应用到 LLM 场景。

第三，看板确认点是流程可治理的关键。状态机流转（进入→设计→预演→评审→交付）+ 每步有责任人，把”AI 自动跑完”变成”AI 跑一半、人接力”。这是 #17（API 安全审计）的”通用 Agent + 业务 Skill”思路的进一步细化——Skill 里有显式的”高风险动作必须人确认”。

但我有 push back：

第一，“持续在线、持久记忆、技能沉淀”三个能力是 Hermes 原生，不是通用 Agent 框架的能力。这篇文章的方法论可迁移，但具体工具可能迁移不了——你用 Claude Code + Memory Engine 也能搭出类似系统，但开发量不小。

第二，流程契约的版本管理没说。能力模块的”输入、动作边界、输出产物”会演化，跟代码一样需要 git 化。否则改几次就成了”屎山”。

第三，看板确认点的人力成本被低估。每个需求 5 个状态流转、每步要人确认——这等于把 AI 提速的部分都赔回去了。实际工程里要根据风险等级分流：高风险走全流程，低风险走自动化跳过。

怎么落到 Agent 项目

核心模块五件套：单 Agent 编排器、能力模块注册中心、看板状态机、规则资产库、结构化工具接口。

  1. 单 Agent 编排器：不要为每个场景写 MultiAgent；用单 Agent + 模块化思维。
  2. 能力模块注册中心：每个模块固化输入、动作、输出、失败、回写——五个契约字段。
  3. 看板状态机：状态流转 + 责任人——这是流程可治理的命门。
  4. 规则资产库：把”老同学才知道”的判断沉淀为可执行规则，配合长期记忆。
  5. 结构化工具接口：高风险动作必须走结构化接口 + 预演 + 人确认。

面试时被问”AI 怎么落地到数据/数仓场景”——直接答”单 Agent 编排 + 多能力模块 + 看板确认”。真正的工程能力不在架构，而在：AI 边界画在哪里、能力模块契约怎么固化、人工确认点怎么放——把这三件事做出来，AI 才从”自动 demo”变成”可治理流程”。

一句话总结

把 AI 边界画在判断前——Agent 负责整理材料和组织证据，人负责业务语义和生产放行；流程可治理的关键不是 LLM 多强，而是状态机、契约固化、确认点这三个软件工程套路。
