把 Agent 当人：AI 组织建设的一个务实视角

2026-08-31 · Agent 组织设计 读文笔记

读文笔记。本文是对他人文章的摘要与评述，非原文转载。 原文：悖论之基于不被当人的Agent建立AI组织 · 凪汐

原文在说什么

大多数关于 AI 组织建设的讨论，都在讲怎么”管理”Agent 这个工具。原文作者认为这是走错了路：Agent 应当以”人”的身份融入既有组织体系，而不是作为一类新工具被纳管。

由此推出一个他称为”平权不等效”的原则：

  • 平权 —— 组织内既有的职能划分和权限设计，对 Agent 同样适用；
  • 不等效 —— 但对 Agent 的绩效要求应当突破人的效能上限。

落到具体设计上，作者把问题拆成两步：

  1. 业务设计中给 Agent 一个位置。把原本绑定在人身上的职能分离出来，定义成独立的业务活动。这与历史上把职能从业务专家身上剥离、下沉到普通岗位是同一类操作。
  2. 系统设计中给 Agent 一个位置。既然 Agent 是人，就继续复用原有的用户权限模型，只在用户身份上打一个类型标签——就像过去区分正式员工与外包人员那样。

文末有一个我认为是全文最锋利的判据：看 token 成本记在谁头上。记在组织账上，你做的是组织结构调整；从员工薪资里划出额度让个人付费，那本质是薪资结构调整，Agent 依然游离在业务设计之外——那就不叫 AI 组织建设，那叫 AI 安全防护。

我的看法

值得认可的部分：它把一个架构问题降级成了增量问题。

工程上，“Agent 是人”最实在的收益是复用 RBAC。如果 Agent 是一类新实体，你需要新的身份模型、新的授权语义、新的审计通道；如果 Agent 只是打了类型标签的用户，那么既有的权限、审批、日志链路全部原样可用，改造面收敛到一个字段。这个判断我认同——它避免了为了引入 AI 而推翻一套已经跑通的组织与系统设计。原文那句”AI 是来提升的，不是来打破的”，放在多数企业语境下是对的。

token 成本归属那个判据也很好用。它把”我们是不是真的在做 AI 组织建设”从一个务虚的表态，变成了一个查账就能验证的事实问题。

我的保留意见：这套推论绕开了责任主体。

人的权限设计从来不只是”能访问什么”，它背后挂着一条问责链——授权、审批、追责、追偿。“Agent 是人”在权限的能力面上成立，但在责任面上不成立：Agent 出错时，审计日志指向的那个 user id 背后没有可追责的主体。

这不是理论洁癖。它会直接反噬作者主张的”不等效”：正因为可以对 Agent 施加人身上不忍施加的 KPI，压力会被推到上限；而一个没有责任约束、只有 KPI 压力的执行单元，恰恰是最容易在边界上做出破坏性行为的。KPI 的上限突破，必须配套责任的显式转移——转移到 Agent 的所有者、审批人或运行团队身上。原文对此没有着墨，我认为这是这套设计落地时会最先炸的地方。

另外，作者把”Agent 比人力市场上能找到的最优秀的人更优秀”作为第一假设，并把不匹配的岗位一律归因于”模型能力暂时不足，需要等”。这个假设过强了。它使整个论证不可证伪——任何失败都可以被解释为时间未到。实践中更可用的做法，是按岗位的可验证性分层：产出能被自动校验的职能优先交给 Agent，产出只能靠人主观判断的职能延后。这条线比”等模型变强”要具体得多。

一句话总结

作为组织设计的起点，“Agent 是人”是个成本很低的好主意——它让你不必推翻重建。但要把它跑到生产环境，得先回答原文没有回答的那个问题：这个”人”，出了事谁负责。
