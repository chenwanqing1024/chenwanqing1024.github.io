得物小摊 Delivery Harness 读文笔记：Version Contract / Evidence Gate 把单人全栈交付拉成可验收

2026-09-15 · Harness AI Coding Agent 交付工程 版本合同

读文笔记。本文是对他人文章的摘要与评述，非原文转载。 原文：得物小摊 AI Native 演进实录：用 Harness 构建可控 AI 交付 · 得物技术

原文在说什么

作者在得物小摊业务里同时负责 H5、运营后台、Node 网关、Go 服务四层。 AI 介入之后，一个人能并行推进多个模块的代码产出——H5 写活动页、后台写运营配置、Node 网关接客户端、Go 服务做底层履约，作者形容为”一个人像拥有了一支虚拟全栈团队”。 但工程半径扩大的同时引入了新风险：跨运行时的业务规则失真、改动越界、验收不可追溯。 原文把这类失真拆成五个控制点——输入偏差、执行越界、验证缺位、缺陷逃逸、反馈断裂。 原文强调它们会级联放大：输入漏掉一条规则，设计里便没有对应分支；测试再锚定已有实现，最终一个不存在的业务路径可能带着”已验证”的标签进入验收。

围绕这五个控制点，原文提出 Delivery Harness 的四组件模型：

  1. Version Contract（版本合同）——锁定事实与边界。每个需求对应一份合同，记录需求列表、各仓库交付范围、测试/预发/验收/生产四态结论。事实按”最接近它的位置”存放：产品口径留在产品文档，影响范围留在规格变更，版本与仓库进入合同，缺陷进入 Repair Case。临时推断不能自动变成长期事实——只有被文档、代码或验证结果确认后，才能进入后续任务的默认上下文。
  2. Execution Boundary（执行边界）——以 Git Worktree 为物理隔离单位。原文给出一条公式：一个需求 × 一个仓库 = 一个 worktree，多仓通过同一份版本合同关联但不共享工作现场。同一需求从开发、UI 与接口联动、联调修复、验收整改到发布收口，全程复用第一次创建的 worktree 和分支。清理 worktree 是合同动作而非便利动作：必须生产发布记录成功、所有提交已推送、证据已持久化，才允许执行 git worktree remove 与 prune，禁止直接删目录、禁止强制移除、也不会自动删除分支。
  3. Evidence Gate（证据门禁）——交付状态之间的不等式写得极其明确：代码完成 ≠ 研发验证通过 ≠ 具备产品验收条件 ≠ 真实环境验收通过 ≠ 生产发布 ≠ 合入稳定分支。统一验收报告是一张”文档—需求—用例—证据”映射表，命令结果、真机截图、运行记录、未覆盖项都能被任何人沿着它找到；缺一项则状态统一保持 pending。原文还预告下一阶段会引入独立评估 Agent（生成与评估分离）来加固门禁。
  4. Repair Loop（修复回路）——把真实反馈写回合同。一条 Repair Case 的完成条件是：在不同提交上，基线失败 + 候选修复通过 + 回归通过，客观上无法建立 red/green 对照时停在较早阶段并说明限制。终点不是复盘文档，而是”下一次同类错误更早失败”——能写成测试的进入测试，能固化为权限边界的进入门禁，能成为版本不变量的进入合同。

原文给出一个完整跨运行时案例：一笔多 SKU 订单从用户端出发，经过管理端、Node 服务、Go 服务，再进入下游系统。 任何一层把”订单”误解成”SKU”都会制造局部正确、整体错误：前端显示完整，后台只处理一部分；接口返回成功，下游却生成多条互不关联的履约记录。 原文的做法是先把唯一不能被拆散的业务不变量写进合同：订单是履约原子单位。 多个 SKU 共享同一次履约决策，要么整单接受，要么整单失败；外部回执必须依靠持久化的稳定标识回到原订单，不能靠当前请求临时猜关联关系。 验收报告记录跨服务结果，每个相关代码仓分别保留分支、提交与发布证据。

最后作者写下了一句提纲挈领的判断：AI Native 改变的不会只是研发效率，也不会停在”产品写 PRD、研发拿 PRD 让 AI 生成代码”。 当需求、版本、实现和证据开始由同一套 Harness 贯通，产研协作的基本单元会从文档交接变成可验证假设——产品定义业务不变量和真实体验标准；研发把它们翻译成接口合同、状态机、门禁与观测；AI 在两者之间持续补全方案、生成实现、构造反例并回放证据。 产品不必等到开发完成才第一次验收，研发也不必等到 PRD 看起来”百分之百完整”才开始工作。

我的看法

我认同作者把”Prompt 写得更好”和”工程系统能接管交付”切成两件事。 AI Coding 早期大家都在卷 prompt 工程，但 prompt 在每次任务里都要重新猜一遍事实、范围和发布锚点，这些本就不该由模型决定。 原文把路径、分支、文档登记、仓库范围、发布锚点从模型手里拿回到确定性系统，本质上是承认：LLM 擅长的是生成，不是治理。 这点我深有共鸣——我自己在做 Agent 项目时也反复发现，一旦把”哪些文件可以改”交给模型自己去判断，跨迭代的稳定性就会被破坏。 反过来讲，给 AI 一个稳定的事实源、明确的可改范围、可追溯的发布锚点，它生成的内容质量反而会显著提升——因为模型不需要把脑力花在”猜上下文”上。

这篇文章给我最有价值的不是”四组件”这四个字，而是”六个状态不等式”和”worktree 清理是合同动作”这两个细节。 前者把”上线”这个最容易被滥用的词拆成可验证的中间步骤，后者把”删 worktree”这种 Git 技巧上升为对发布证据链的检查。 前者是工程口径，后者是流程纪律，两者一起把”我能交付”变成”我能证明我交付过”。 原文还有一个细节容易被忽略——Evidence Gate 不仅要验收报告完整，还要”答不全，状态就停在原地”，这是一种”宁可阻塞也不假装通过”的工程勇气。 配合”AI 可以整理证据，不能替责任人签字”的边界声明，整个 Evidence Gate 才真正站得住——它是工具与责任的分工，不是工具替代责任。

三个反直觉的工程判断：

  1. worktree 不是 Git 技巧，而是 Execution Boundary 的物理实现——很多人把 worktree 当成”在另一台机器上同时改代码”的便利手段，但原文把它定义为”一个需求 × 一个仓库 = 一个 worktree”。这把”需求隔离”变成文件系统级别的强制约束，AI 没法绕过。Worktree 的清理动作也被纳入了发布证据链——这等于把”删工作树”从个人行为改造成合同动作。我在做 Agent 平台时也观察到类似规律：物理隔离比权限策略更难被绕过，边界设计的第一性原理就是”让错误的空间不重叠”。
  2. “代码完成”与”生产发布”之间至少有四个不等号——这条链如果不断开，所有团队都会陷入”测试说通过了但线上炸了”的循环；原文的 Evidence Gate 把每个不等号都配上独立证据位（编译、单测、接口验证、真实设备、生产发布、稳定分支合入）。原文还特别强调”AI 可以整理证据，不能替责任人签字”，把责任边界划得很清楚。这等于承认：自动化可以验证事实，但无法代替人做出体验判断。
  3. Repair Loop 的产物不是文档而是”下一次默认行为”——能写成测试的进测试，能固化为权限边界的进门禁，能成为版本不变量的进合同。如果一轮故障只换来一段复盘，那 Loop 实际是断的。这把”经验沉淀”从叙事任务升级为系统级行为变更。原文还顺手解决了”环境恢复不能写成代码修复；偶现问题不能因为暂时没复现就宣布解决”两个隐形漏洞——这两条几乎所有复盘文档都会犯。

但我有 push back：

  1. 原文对 Execution Boundary 的实际越界场景描述偏少。比如：AI 自行修改测试用例让单测通过、跨仓改动声明后偷偷扩大范围、AI 自创配置文件绕过统一请求层——这些是 Harness 真正会遇到的对手，文章只给了原则，没有给出被破门后的”二阶防线”。如果越界没有被工程化拦截，Worktree 就只是文件夹标签而不是真正的边界。一个 Harness 的成熟度，往往不是看它能挡住多少”显然的越界”，而是看它在遇到”看起来合理的越界”时怎么反应。
  2. Repair Loop 的样本量没有给出。原文写到”基线必须失败 + 候选修复必须通过 + 回归必须通过”的红绿对照要求，但这只是单条 Case 的完成条件，跨团队 / 跨周期累计多少条 Case 才形成系统级行为变更？20 条？200 条？这条门槛缺失会让”Repair Loop 真正升级到合同层”沦为口号。团队很容易停留在”完成 5 条 Case 就觉得 OK”的水平，错过真正的经验沉淀窗口。
  3. 独立评估 Agent 这条最关键的演进，作者只给了方向（生成与评估分离），没说它的输入契约、拒绝标准、是否复用同一份证据 Gate。如果评估 Agent 也跑在同一组证据上，“独立”两个字会站不住脚——评估者一旦能看见生成过程的 prompt，就已经在认知层与生成者耦合了。一个真正独立的评估 Agent 必须用另一份事实源、另一组 prompt 模板、另一个模型实例，三者同时切换才有意义。

怎么落到 Agent 项目

如果让我基于这篇搭一个”单人全栈交付 Agent”的项目，我会画五个模块：

  • Version Contract 注册中心：用 YAML/JSON 描述需求 ID、各仓库 commit 范围、状态字段；状态字段机读，禁止字符串拼接。合同本身版本化，每次修改留 diff，可回放。
  • Worktree 编排器：监听 Issue 事件，按”一个需求 × 一个仓库”自动开 worktree，清理动作必须等”发布证据全部落库”信号。删除操作幂等，必须由发布后系统回调触发，不允许人工触发。
  • Evidence Gate 检查器：六个状态每个挂一份 evidence（编译产物、单测报告、接口契约、真实设备截图、生产发布 tag、稳定分支 PR），任何一项缺失状态机都不前进。证据文件本身 hash 化，避免”截一张图就声称通过”。
  • Repair Case 跟踪表：每条 Case 强制要求 baseline/red/green/regression 四个 commit hash，未填齐不允许 close。Case 状态分为 open / awaiting-evidence / verifying / closed / archived 五态。
  • 独立评估 Agent：只读取 Issue、diff、evidence 三件套做判定，输入面与生成 Agent 完全隔离，输出三态（accept/reject/need-more-evidence）。评估 Agent 内部状态不可被生成 Agent 探查。

面试如果被问”你怎么做单人 AI 全栈交付”，可以这样答：靠 prompt 提速，但靠合同和证据守住交付；worktree 是物理边界、evidence gate 是流程边界、repair loop 是时间边界；三者咬合之后，AI 才能从一次性的代码生成器变成长期可被审计的工程单元。我会特别强调”AI 整理证据、人签责任”的边界——速度由模型放大，质量秩序必须由系统托底。

一句话总结

AI Coding 的真正瓶颈不是模型会不会写代码，而是交付状态能否被合同、边界与证据守住——Delivery Harness 的四组件本质上是在给模型盖一座”可被审计的脚手架”，而不是教模型更聪明。

延伸思考：把这篇当面试 Project 引子

如果面试官要我拿这一篇当 Project 讲，我会分三层讲：

  • 机制层：四组件怎么咬合、状态机怎么推进、证据怎么 hash 化。
  • 数据层：每个需求的 evidence 字段怎么写入、合同变更怎么追溯。
  • 治理层：AI 整理证据、人签责任、独立评估 Agent 怎么防止”评估者与生成者耦合”。

这三个层次对应的就是”机制可信 / 状态可查 / 责任可追”，也是 Harness 工程区别于普通 AI Coding 的全部秘密。

一句话补记

回到一句话：四组件的本质不是”防 AI 错”，而是”让 AI 错的位置早暴露、证据早固化、追溯早可查”。如果面试被追问”四组件最容易被砍的是哪个”，我会答 Repair Loop——因为它最慢见效、最难量化、最容易被当作”复盘文档”草草处理。但失去 Repair Loop，四组件会退化成三件套，闭环断开。
