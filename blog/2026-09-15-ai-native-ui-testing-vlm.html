读文笔记：AI Native UI 测试——VLM 跨平台统一与自愈

2026-09-15 · AI Native VLM UI 测试 自愈 跨平台

读文笔记。本文是对他人文章的摘要与评述，非原文转载。 原文：AI UITester：AI Native 的 UI 自动化测试新范式｜得物技术 · 得物技术

原文在说什么

得物 ai_uitester 把 UI 测试从”基于元素定位”重新定义为”基于视觉理解”。核心是 VLM 作为执行引擎，“截图→理解→执行”闭环替代传统 Appium/Selenium 的”找 ID/XPath 再点击”。

三大能力：

能力一：用例平台数据自动转化。 内部测试用例平台导出的 JSON 是多层树形结构（目录+用例节点，数百个节点、上百条用例、最大深度十余层）。自动化 Pipeline 6 阶段：树结构展平 → 用例解析 → 去重 → LLM 增强（核心）→ 持久化 → 版本归档。LLM 增强模块把”描述性用例”（如”某列表正常展示，可滑动查看更多”）转化为”可执行脚本”（App/Tap/Wait/Assertion/Swipe 步骤）。支持并行增强与断点续传，模块级 Wiki 预加载避免重复调用。Wiki 知识库是嵌入 ai_uitester 多个核心模块的基础设施层，被 5 大场景消费。

能力二：AI 智能调试与用例自愈。 失败先用规则引擎分流：device/timeout/network 走自动换机或重试；business 失败才进 AI 诊断。AI 诊断输入：✓✗○ 标注步骤 + 错误信息 + 失败截图 + Wiki 知识；输出：diagnosis + confidence + complete_steps + resume_from_index。置信度阈值 0.5——> 0.5 自动应用修复并替换执行步骤，< 0.5 弹出人工审核（Accept/Reject + 倒计时超时自动 Reject）。

三个真实自愈案例：

  1. UI 变更按钮位置移动（confidence 0.9）：原始”点击底部工具栏按钮”失败，修复为”点击页面顶部功能菜单栏对应按钮”；
  2. 进入页面需要额外操作（confidence 0.8）：点击入口未进目标页面，插入等待 + 再次点击；
  3. 冷启动弹窗遮挡后续步骤（confidence 0.9）：AI 诊断洞察中间步骤虽标记为 ✓ 但实际未产生预期效果，标记”前置步骤失效”回退到步骤 2，启动 App 后插入条件 Action 处理弹窗。

置信度铁律： (1) MatchedText 必须从截图中逐字符复制，不允许脑补；(2) 宁可不点击也不点错。

能力三：VLM 驱动的跨平台统一。 VLM 看到的是像素级截图（不是 DOM），所以同一套指令三端通用、天然免疫 UI 变更、所见即所得。统一 API 接口（操作/断言/查询/等待）屏蔽底层平台差异。底层驱动根据设备类型自动选择（Appium/Hypium/自研），上层代码完全无感知。

BaseAIDriver 核心循环： “截图→大模型解析→决策执行→记录日志→重新截图”，最多 20 轮，点击配套置信度校验。开启深度思考模式后，模型获得子目标分解、进度跟踪（✓/→/○ 可视化）、前后截图对比三项能力。

架构取舍：

  • 为什么”逐步执行”而非”一次规划”？UI 测试的核心挑战是状态不确定性——每步操作后屏幕变化，预先规划基于过时信息。代价是单次最多 20 轮 LLM 调用。
  • 为什么自愈返回完整步骤列表而非增量 Diff？增量 Diff 在多次修复后索引偏移，完整列表更可靠，代价是 Token 消耗更大但避免”修复引入新 Bug”。

五层降级匹配： 精确匹配 → 去除优先级后缀 → 去除括号 → LLM 语义匹配 → 跳过并缓存。“宁缺毋滥”原则：错误知识比无知识更有害。

我的看法

我认同： “AI Native 方案的假设是 UI 一定会变，所以让 AI 理解变化并适应变化”——这是测试哲学的根本转变，从”抵抗变化”到”拥抱变化”。传统方案和 AI 辅助方案的隐含假设都是”UI 不变”，所以需要人维护定位器；一旦接受 UI 一定会变这个前提，整个测试架构就重写了。这是文章给我最大的范式冲击。

这篇文章给我最有价值的不是 VLM 本身，而是”逐步执行”vs”一次规划”的判断。 UI 测试的核心挑战是状态不确定性——每步操作后屏幕变化，预先规划会基于过时信息。所以 ai_uitester 选最多 20 轮的”逐步执行”，每步重新截图重新决策。这个决策的反面是”一次规划 + 重试”——后者更省 Token，但每次重试都在错误的基础上规划，越走越偏。状态不确定性是 UI 测试的根本特征，决定了执行模型的选择。

反直觉的工程判断：

  1. 置信度阈值 0.5 不是拍脑袋数字，是”通过即正确”的实测调优。 阈值过高则大量操作被拒绝、执行效率低；阈值过低则误点风险上升。文章明确说”经过大量实测调优，在准确率和覆盖率之间取得平衡”。UI 测试的特殊性在于”点错位置比没点危害大得多”——置信度阈值本质是”宁可漏点不可误点”的产品决策。

  2. 完整步骤列表优于增量 Diff 的决策很反直觉。 增量 Diff 省 Token，但多次修复后索引偏移、修复引入新 Bug 是常见问题。完整列表虽然 Token 消耗大，但每次修复都是”全量替换”，不会出现”修复 A 坏了 B”。Token 成本可以靠缓存和去重优化，逻辑正确性无法靠优化补救。

  3. 失败分类器把 80% 的失败在规则层就处理掉，AI 诊断只处理 20% 的业务失败。 device/timeout/network 走自动换机或重试，根本不进 AI 诊断。这是”用规则过滤噪音、用 AI 处理信号”的经典分层设计——AI 调用次数 = 总失败数 × 业务失败率。如果不做这一步分层，AI 调用成本会爆炸。

但我有 push back：

  1. 最多 20 轮的逐步执行，单次用例成本没有量化。 一条用例平均跑多少轮？月度 Token 成本是多少？与传统 Appium 方案的成本对比？这些数字都没有，“AI Native”在 ROI 上的说服力打了折扣。对于预算敏感的团队，这套方案能不能落地要打个问号。

  2. VLM 模型选型没说。 文中提到 Qwen2.5-VL-72B 是另一篇文章的能力二，本篇 ai_uitester 用的是哪个 VLM？GPT-4V 还是 Qwen 还是 Gemini？不同 VLM 的截图理解准确率差异很大，不说模型就没法复现也无法评估替换成本。

  3. “五层降级匹配”具体在哪一层触发没说。 比如”精确匹配”和”去除优先级后缀”的判断逻辑是什么？“LLM 语义匹配”调用的是哪个模型？“跳过并缓存”缓存的是结果还是失败原因？Pipeline 缺了关键的实现细节，复现时只能猜。

怎么落到 Agent 项目

面试被问”如何设计 AI Native 的测试系统”时的回答框架：

  • 用例生成模块： 用例平台 JSON 自动转化 Pipeline（树展平 + LLM 增强 + Wiki 预加载 + 断点续传 + 五层降级匹配），LLM 把描述性用例转化为可执行步骤；同一模块的用例共享 Wiki 缓存避免重复调用；
  • 执行引擎模块： VLM 作为执行引擎，统一 API 屏蔽平台差异，底层驱动自动选择（Appium/Hypium/自研），BaseAIDriver 实现”截图→理解→执行”循环最多 20 轮；
  • 失败分类与自愈模块： 规则引擎先分流（设备/超时/网络 vs 业务），业务失败才进 AI 诊断；置信度阈值 0.5 决定自动应用还是人工审核；自愈返回完整步骤列表而非增量 Diff；置信度铁律 = MatchedText 逐字符复制 + 宁可不点不错点；
  • 知识库模块： Wiki 知识库嵌入 Pipeline / 增强 / 诊断 / 匹配多个模块，“宁缺毋滥”原则贯穿；五层降级匹配（精确→去后缀→去括号→LLM 语义→跳过缓存）；
  • 跨平台抽象模块： VLM 看截图不看 DOM，同一 JSON 三端通用；深度思考模式给模型子目标分解 + 进度可视化 + 前后对比能力。

工程落地实践

分阶段里程碑：v0.1 用例平台 JSON 接入 + 树展平 Pipeline（无 LLM，纯规则）→ v0.5 加 LLM 增强（Wiki 预加载 + 断点续传）→ v1.0 接 VLM 执行引擎（BaseAIDriver + 三平台驱动）+ 最多 20 轮循环 → v1.5 上失败分类器（规则先分流 + 业务失败进 AI 诊断）→ v2.0 加跨平台统一执行（同 JSON 三端跑）。每阶段必须有”用例转化成功率”和”执行成功率”两条基线。

关键数据契约：TestCaseJson(steps[], assertions[]) + WikiCache(module_id, summary, last_updated) + FailureClass(category, confidence, fix_suggestion)。三件套进数仓做长期分析（哪些模块 LLM 增强效果最好、哪些失败分类高频出现）。

常见踩坑 + 兜底：(1) LLM 增强成本失控 → Wiki 缓存强制复用 + 同模块用例共享；(2) VLM 决策置信度低 → 阈值 0.5 是分水岭，低于阈值强制人工审核（“宁可不点不错点”是铁律）；(3) 失败自愈引入新 bug → 自愈返回完整步骤列表而非 Diff，避免”看起来修了但其实更糟”；(4) 截图分辨率影响 VLM 准确率 → 强制统一缩放到 1080p，元素区域单独裁剪；(5) 跨平台差异 → VLM 看截图不看 DOM，强制底层驱动不暴露 DOM API 给上层。

一句话总结

AI Native UI 测试的本质不是”用 VLM 替代元素定位”，而是”以截图→理解→执行闭环替代基于 DOM 的查找-点击模型 + 置信度机制 + 完整步骤自愈 + 失败分类规则引擎”——这是测试哲学从”抵抗变化”到”拥抱变化”的根本转变。
