## 原文在说什么

得物这篇讲的是网关路由 AI 安全审计系统，覆盖数万个 API、上百个微服务的全量审计场景。

架构核心是**通用 Agent + 业务 Skill 分层**：常规代码负责任务调度与结果存储，所有 AI 分析工作由超级 Agent 完成。底层用 Claude Code / OpenCode 这种成熟 Coding Agent，把代码理解、推理分析、上下文管理、会话恢复等通用能力直接复用——**不重复造轮子**。业务逻辑（检测规则、分析流程、报告格式）全部沉淀在 Skill 中，可以随时调整优化。

具体项目分析时采用 **AI 批量筛查 + 人工深度验证的人机协同模式**：

```
AI Agent
├─ Step 1: 路由配置检查（auth_config.public、required_scopes）→ 短路退出
├─ Step 2: 登录态识别（认证节点存在性）→ 标准认证路由直接信任
├─ Step 3: 代码审计（三维检测）→ @PreAuthorize 注解 / 用户 ID 来源 / 所有权校验
└─ Step 4: 精细化危害评估 → 越权读取 / 越权操作
```

检测分四步，前两步设有短路退出以降低成本。配置无异常、认证路由标准，可以直接跳过代码审计。

**Skill 层**结构很清晰：

```
gateway-route-vuln-analyzer/
├── SKILL.md                        # 核心：漏洞分析主流程
│   ├── 检测决策树（Step 1-4）
│   ├── 危害评估规则
│   └── 报告输出模板
├── references/
│   ├── unauthorized_patterns.md    # 越权漏洞模式库
│   ├── logic_flaws.md              # 逻辑漏洞检测指南
│   ├── data_classification.md      # 数据敏感性分级
│   └── report_template.md          # 标准化报告模板
└── scripts/
    └── mcpcli-gateway              # CLI入口（Token优化）
```

**精细化危害评估**是这篇文章的工程亮点：越权读取走**数据敏感性评估**（依据《数据安全法》《网络安全法》对数据资产分级），越权操作走**利益流向评估**。这避免了"一刀切"评级——同样是越权，读用户头像和读订单信息、修改昵称和退款是完全不同的危害等级。

**Token 成本降低 95%** 的优化策略值得逐条记：

1. **MCP → CLI 转换（mcp2cli）**：把 MCP 工具暴露为 CLI 命令，避免每次会话加载 MCP 上下文。效果：节省 61% Token。
2. **工具返回值优化**：`gitlab_file` 无参数调用会返回完整文件（最大 1.47MB ≈ 500K tokens）。加精准参数实现按需提取。效果：v2 vs v1 再节省 88%。
3. **Early-Exit 模式**：标准认证路由直接信任，跳过冗余代码审计。效果：节省 50-70%。
4. **AI 友好返回格式 YAML**：YAML 天然比 JSON 的 Token 量更少，对 AI 阅读更友好。

**模型选型**建立了 P0/P1/P2 三重约束下的决策矩阵，最终选了 qwen3.5-plus——在召回率 100% 的候选模型中，以更低的单位成本实现可接受的准确率，是批量场景下的最优解。

作者明说：测试集基于独立手工标注测试集（100+ 样本），与生产告警数据相互隔离，仅作基线参考；大模型迭代速度快，可能存在更优模型未纳入评测。**局限性的诚实标注本身就是工程素养**。

## 我的看法

我认同作者把"通用 Agent + 业务 Skill 分层"作为垂直 Agent 应用架构起点的判断。这是过去一年最被低估的一个 Agent 落地范式——很多人以为做 AI 应用必须自己写 Agent 框架，其实成熟的 Coding Agent 已经把通用能力做完了，业务方只需要在 Skill 层做领域封装。

但这篇文章给我最有价值的不是架构本身，而是几个工程判断：

第一，**Token 成本降低 95% 不是优化，是生存问题**。一个审一万条 API 的 Agent，原始 MCP 调用方式下 Token 消耗足够把任何模型账单打爆。文章给的四个优化点（mcp2cli / 参数精准化 / Early-Exit / YAML 返回）其实是工程常识，但在 LLM 应用里被严重低估——因为大家习惯了"调 LLM = 烧钱"。**做 LLM 应用的第一步是控制 Token 消耗，而不是选择哪个模型**。

第二，**短路退出是减少无效调用的关键**。前两步配置检查和登录态识别可以快速过滤掉 80% 的合规路由，只对真正可疑的路由跑完整代码审计。这种"早退 + 深度"的策略跟编译器优化、数据流水线是同一个套路——**先做廉价检查，再做昂贵分析**。

第三，**危害评估分两类（读取 vs 操作）是反常识的正确设计**。普通的安全工具用单一严重等级（高/中/低）评估漏洞，但实际工程里同样是越权，"读他人订单"和"替他人退款"的业务影响差 100 倍。**业务驱动的风险评级 > 通用 CVSS 评分**。

但我有几个 push back：

第一，**人机协同的具体边界没说**。AI 批量筛查后哪些场景走人工深度验证？判断标准是什么？是所有 P0 都人工？还是 AI 标记"不确定"的才人工？这直接影响人工成本和系统可用性。文章只在概念上提到"AI 处理重复筛查，人工聚焦深度分析"，但没给出 SLA 量化。

第二，**Skill 层的设计模式**值得推广但没说怎么避免 Skill 膨胀。一个项目的 Skill 可能从 5 个涨到 50 个，怎么管理？版本控制？测试？复用？这跟微服务架构的"服务网格"问题很像——抽象做对了能复用，做错了反而是负担。

第三，**召回率 100% 的要求**。文章说模型选型"召回率 100%"——这是不是要求过高？100% 召回意味着漏报为零，这通常需要牺牲精度（多报）。一个更现实的目标是"高召回 + 可接受误报 + 人工兜底"。文章的"人工深度验证"是兜底，但没量化人工成本。

### 怎么落到 Agent 项目

如果让我基于这篇做一个**垂直 Agent 应用（不限于安全审计）**，我会画成这样：

**核心模块四件套：通用 Agent 基座、Skill 注册中心、决策树短路、Token 优化器。**

1. **通用 Agent 基座**：直接用 Claude Code / OpenCode 这种成熟 Coding Agent，不要重新发明轮子。它们的代码理解、推理、上下文管理、Session 恢复都已经是产品级。

2. **Skill 注册中心**：每个业务场景一个 Skill，结构 = SKILL.md（决策树） + references/（知识库） + scripts/（CLI 工具）。**references 不进 context**，按需检索；scripts 是 Token 优化的关键。

3. **决策树短路**：先做廉价检查（配置、登录态）再做昂贵分析（代码审计）。**短路退出条件要明确可测**，不能凭"AI 觉得没问题"。

4. **Token 优化器**：四个手段叠加——
   - MCP → CLI 转换
   - 工具参数精准化（按字段提取，不返全文件）
   - Early-Exit 模式
   - YAML 返回格式

**工程上最值得做的：**

- **业务驱动的风险评级**：按"读取 vs 操作"、"公开数据 vs 私密数据"、"无利益 vs 有利益"分维度评估，不要用单一严重等级
- **测试集独立标注**：手工标注 100+ 测试集，与生产数据隔离，避免过拟合到测试集
- **局限性诚实标注**：在文档里写明"测试集局限""模型迭代风险"，不是谦虚是工程素养

**面试时被问"AI Agent 怎么落地垂直场景"**——直接答通用 Agent + 业务 Skill 分层。**真正的工程能力不在分层本身**，而在于：短路决策、Token 优化、危害分级、测试集隔离——把这四件事做出来，垂直 Agent 才从 PoC 变成产品。

## 一句话总结

AI Agent 做垂直场景的关键不是"自己造 Agent 框架"，而是复用通用 Agent + 在 Skill 层做领域封装；同时把 Token 优化、决策树短路、危害分级当成头等工程问题对待——这四件事做对了，垂直 Agent 才从烧钱 demo 变成能上生产的产品。
