## 原文在说什么

得物社区运营搭一场营销活动的原始流程：打开 A 系统创建话题、切到 B 系统填写活动配置、再打开会场搭建系统配置组件，最后提交审核——3 个系统间跳转 10+ 次、填 40+ 字段，字段高度耦合（活动名改一个字 3 个地方都要改）。

**第一版（失败）：** 5 步表单向导 + 2 个 Dify Workflow（文档解析 + 语义匹配）。运营从"全部手填"变成"AI 预填 + 人工校验"。结果是"操作时间缩短了，但远没有达到质的飞跃"——原因是范式没变，运营仍是流程主体，AI 只是预填了一部分字段。问题清单：还是要理解每个字段、按顺序走完 5 步、在三个系统间跳转、自己判断 AI 填得对不对。

**Agent CLI 评估（否决）：** OpenCode CLI、Cursor、Claude Code 这类工具展示了完全自主 Agent 的可能性。但落地有三个硬障碍：Agent 对会场业务约束没"体感"；Agent 无法获取实时状态；Agent 操作缺少审计与可解释性。最终选择 Anthropic Agentic 系统复杂度光谱中间位置——Prompt Chaining + Routing + Human-in-the-loop 组合。

**第二版（成功）：** Workflow 模式而非纯 Agent。LangGraph 作为编排引擎（MIT 开源、有向图 + Checkpointer 持久化 + interrupt/resume 机制）。前后端交互基于 LangGraph 的 interrupt/resume：后端流程到需要人输入的步骤时 `interrupt()` 暂停，把结构化 payload 发给前端；前端根据类型渲染 UI 卡片；用户操作后 `Command(resume=value)` 推回去继续。

**6 个中断点**对应 Anthropic Human-in-the-loop 的几类动作：Approve/Reject（高风险前确认）、Edit（修改 Agent 中间结果）、Respond/Input（提供 AI 拿不到的数据）。

**Capability Registry：** 类似微前端的 Module Federation。前端壳不写死场景，每个业务场景注册"能力模块"（欢迎态、中断卡片、结果展示）。新增场景只需注册一个新模块，不改壳代码。当前已接会场搭建、动态筛选、通用聊天三个场景。粒度比微前端更细——不是整个页面模块的联邦，而是 UI 贡献点级别的注册。

**组件模块协议：** 解决"16+ 个会场组件的配置逻辑差异大"问题。每个组件抽象成独立模块，定义统一生命周期（解析 → 选组件 → 补字段 → 确认 → 构建）。**最重要规则：初始化阶段不产生副作用（不能调后端创建资源），真正写操作必须在"构建前"阶段**——这个规则避免了一个真实 bug：有组件在初始化时偷偷调后端保存接口，导致用户只是打开卡片看一眼就创建了活动数据。双轨注册：显式选择（用户手动加）+ 条件注入（系统根据规则自动加，但展示"已自动注入"提示）。

**第三版（演进）：** 第二版前提是运营有策划文档，第三版前提是运营只有活动想法。两阶段架构：

- **Stage 1 活动方案生成 Skill（只读不写）：** 只查候选数据（预算池、类目、标签、历史会场），不做任何写操作。所有写操作（创建话题、创建活动、复制会场、提交审核）全部由 Stage 2 闭环。"只读"约束是权限模型的设计选择，不是技术限制。引导策略是渐进式信息收集（Progressive Disclosure）：最低三件套（活动名 + 时间 + 至少一个话题），其他信息按对话进度逐步追问。
- **Stage 2 聚合工作台：** 独立页面而非聊天壳面板，承载更偏生产操作的密集交互。中栏预览复用搭建器已有的 H5 编辑页面 + 覆盖一层可交互遮罩，运营点击预览组件 → 右侧自动展示该组件配置表单。草稿实时同步保证操作不丢失。组件级 AI 改造：显式 AI 辅助面板（AI 辅助/原表单切换）+ 通用自然语言编辑（选中组件上下文交给后端编辑子流程）。

**Form Host 妥协：** 搭建器的组件表单依赖特定运行时和 Formily 引擎，不重写几十个组件表单，做独立构建通过消息协议与主页面通信——把开发精力放在真正新增的价值上（预览交互、AI 辅助、草稿同步），不重造已有轮子。

## 我的看法

**我认同：** "如果 AI 的角色只是帮你填字段，它永远不会带来质变"——这是整篇文章最值钱的认知。GitHub Copilot 从行级补全进化到 Copilot Workspace，ChatGPT 从对话进化到 GPTs+Actions，都是同一个拐点（AI 从辅助工具变成流程主体）。把运营从"流程执行者"变成"流程监督者"——这个角色重新定义才是 AI 产品价值跃迁的真正杠杆。

**这篇文章给我最有价值的不是 LangGraph interrupt/resume 的具体 API，而是"Workflow vs Agent 的判断法则"。** 文章给的经验法则：流程能画成有限状态机图 → Workflow；更像"给定目标让 AI 自己想办法" → Agent；大多数企业级场景是两者的混合（大框架 Workflow 保证可控，局部节点 Agent 提供灵活性）。这与 LangChain 创始人 Harrison Chase 的判断一致——"当前大部分成功的 AI 应用都是 Workflow 而非 Agent"，连 Klarna 的 AI 客服系统被宣传为 Agent，实际架构也是 Workflow（明确的意图分类路由 + 标准化的工具调用流程 + 人工 escalation 机制）。

**反直觉的工程判断：**

1. **"初始化阶段无副作用"是组件模块协议的核心安全条款，不是技术限制，是权限模型设计。** 这条规则与 AWS IAM 最小权限原则一脉相承——每个主体只拥有完成当前任务所必需的最小权限集。如果初始化能写，用户"看一眼"就触发了数据变更；只有"构建前"才能写，用户意图被强制确认。这个规则防住的 bug 是真实发生的。

2. **Capability Registry 比微前端 Module Federation 粒度更细。** 微前端联邦的是整个页面模块，Capability Registry 联邦的是 UI 贡献点（欢迎态、卡片、结果展示）级别的注册。这种粒度更适合"壳不关心业务、只调度渲染"的场景，新增能力只需注册新模块。粒度选择决定了扩展成本。

3. **Stage 1 只读不写是渐进式权限设计。** Stage 1 给读权限（查预算池、类目、历史会场），Stage 2 逐步开放写权限（创建话题、创建活动），发布权限要求人工确认后触发。三级权限阶梯 + 人工 gate，是企业级 Agent 落地的务实模式，避免"一上来就开放所有权限"的安全灾难。

**但我有 push back：**

1. **"中断恢复"的具体持久化方案没说。** LangGraph Checkpointer 把状态写到哪？Redis 还是 Postgres？跨会话、跨浏览器的恢复粒度是多少？文章说"关掉浏览器再打开可以继续"但没给持久化层设计——一个企业级特性，缺持久化方案描述等于没设计。

2. **Form Host 妥协的工程债没有评估。** "独立构建通过消息协议与主页面通信"——这个方案后续维护成本是多少？组件表单迭代时要同步改两个仓库吗？这个妥协对长期演进的影响没讨论，可能在 6 个月后变成不可维护的双轨地狱。

3. **没给 Stage 1 Skill 的实际效果数据。** 只说"渐进式信息收集，最低三件套（活动名+时间+话题）"，但用户跑完整流程的平均对话轮数、生成策划文档的可接受率（运营需要返工的比例）、从想法到上线的端到端时间——这些指标都没给。方法论没数据支撑就是空中楼阁。

### 怎么落到 Agent 项目

面试被问"如何设计企业级 AI Agent"时的回答框架：

- **范式判断模块：** 业务流程画成有限状态机 → Workflow（LangGraph）；给定目标让 AI 自己想办法 → Agent；混合场景大框架 Workflow + 局部节点 Agent；
- **Interrupt/Resume 模块：** 后端 `interrupt()` 暂停 + 持久化 Checkpointer（Redis/Postgres）+ 前端 Capability Registry 渲染卡片 + `Command(resume=value)` 恢复；6 个中断点对应 Approve/Reject/Edit/Respond 四类动作；
- **权限分级模块：** Stage 1 只读（查候选数据）→ Stage 2 写（创建资源）→ 发布（人工确认），与 IAM 最小权限原则对齐；渐进式披露 Progressive Disclosure 降低用户认知负担；
- **组件协议模块：** 统一生命周期 + "初始化无副作用" 硬规则 + 双轨注册（显式选择 + 条件注入 + "已自动注入"提示），符合开闭原则；
- **工程妥协模块：** 复用已有运行时 + 独立构建 + 消息协议通信，把开发精力放在真正新增的价值上，不重造已有轮子；但要在事前评估长期维护成本。

### 工程落地实践

**分阶段里程碑**：v0.1 把 3 个系统的"运营填 40+ 字段"流程画成有限状态机，先做 Workflow 不加 Agent → v0.5 在工作台聚合 Step1 必填项 + Step2 可选 → v1.0 上 Stage 1 必填 Skill（活动名/时间/话题）+ Agent 自动查资源 → v1.5 接 Interrupt/Resume + Checkpointer（Redis）→ v2.0 上 Stage 2 写权限 + 发布双签。每阶段必须有"运营从想法到上线的时间"基线。

**关键数据契约**：`ActivityContext(activity_id, fields{}, history[])` + `InterruptDecision(approve/reject/edit/respond)` + `Stage2Manifest(created_resources[])`。三件套进数仓做长期分析（哪些活动审批通过率高、哪些 Stage 2 资源经常被返工）。

**常见踩坑 + 兜底**：(1) Agent 跑飞无限循环 → 状态机强制 Stage 1 → Stage 2 → 发布三阶段，每阶段必走 Interrupt；(2) Checkpointer 膨胀 → 90 天前的 Activity 自动归档 + 冷数据转 OSS；(3) Stage 2 误操作 → IAM 最小权限，AI 只用专用 token 而非 admin token；(4) 用户改 1 个字段 3 个系统全要同步 → 工作台聚合视图 + 字段变更事件总线；(5) Interrupt 卡片渲染不一致 → Capability Registry 注册中心统一组件契约。

## 一句话总结

企业级 Agent 落地的关键不是"AI 多强"，而是"Workflow 与 Agent 的混合范式 + Interrupt/Resume 的人机协作语言 + 渐进式权限分级 + 初始化无副作用的安全约束"——AI 从辅助工具变成流程主体，才是产品价值跃迁的真正拐点。
