## 原文在说什么

得物技术「行亦」这篇讲的是**交易核心系统在 AI Coding 时代的稳定性治理**。背景矛盾很尖锐：AI 让代码产出又快又多（人均增加近 3 倍），但**质量不会因生成速度提升而自动提升**——约束不够强、知识不够全，AI 就会「又快又稳地把错的东西复制一千份」。

作者的核心论断:**问题不在 AI 不会写代码,而在旧流程没有给 AI 准备可执行的输入和可验证的出口**。旧流程是为「人理解人」设计的(PRD 给人读、代码给人审、测试靠经验),AI 编码要重新设计的不是 AI,而是它工作的流水线。

订单系统耗时一年多完成三阶段改造(稳定性兜底 / 核心链路隔离 / 架构模块化),AI Native 阶段把研发流水线重构为**五道标准化关口**:

**第一道关口:需求澄清(保证方向不错)**
- 用 Gherkin(BDD Given-When-Then)写验收场景,需求、测试、实现三者一一对齐
- Spec 固定六节模板(基本信息 / 业务目标 / 核心流程 / 边界条件 / 业务规则 / 优先级),强制业务语言屏蔽技术术语
- 知识库兜底现状:澄清开始前自动从知识库 + 代码现状拉「现状分析报告」,避免 AI 凭空假设
- 提问管理:按「该问 / 不该问 / 可跳过」分类管理提问,防止 AI 过度问或漏问

**第二道关口:技术方案设计(锁定「怎么改」)**
- 五段式模块拆解:目标 / 变更位置 / 字段配置 / 处理逻辑 / 阻断兜底
- 跨环节不变约束从知识库拉取,逐条让用户选「纳入 / 明确排除」,排除必须填理由(门禁阶段复查)
- 统一技术方案模板:业务用例分析 → 整体架构 → 场景详细设计 → 数据结构设计 → 稳定性设计
- 稳定性维度强制可灰度 / 可监控 / 可回滚,弱依赖补全熔断降级链路

**第三道关口:TDD 编码实施**
- 技术方案拆成可独立验证的任务列表,每个任务有入口(失败测试)+ 出口(通过测试)
- 编码前架构预检(事前防比事后查成本低)
- RED-GREEN 循环:先写测试再写代码,每行代码有对应测试、测试对应到 Gherkin 场景
- 关键判断:AI 写代码最大的问题不是写不出来,而是它太自信——没有 TDD 的「完成」是主观判断,有 TDD 的「完成」是测试通过——客观可验证

**第四道关口:门禁卡控(三层 DAG + 增量体检)**
- 审核不止在 gate-check,每个阶段产物落地都有对应审核 Agent,gate-check 最终汇总
- 三层 DAG 结构:层内并行、层间串行
- 增量代码体检:9 个维度扫描本次改动(新增外部调用 / 线程池 / 错误码重复 / 关键调用链),结果发飞书知识库

**第五道关口:全流程埋点监控**
- 三层看板从需求 → 方案 → 代码逐层下钻
- 五个观察维度:耗时、对话轮数、知识库命中率、门禁通过率、回退根因
- 三个驱动改进场景:知识库补充(从用户问答挖该补什么)、流程优化(耗时+对话轮数异常 = 流程设计问题)、子代理与工具调用收敛(谁在白干)

## 我的看法

我认同:这篇文章把「AI Coding 落地难」的根因诊断得非常准——**问题不在 AI,在流程**。很多团队买更好的模型、换更贵的 IDE,结果代码质量没提升,根因就是旧流程让人参与的部分没为 AI 重构。AI 不能「猜」PRD 是什么意思(写代码的人能猜、测试的人能猜,折损两次),必须把需求变成「机器可读、可执行」的硬契约(Gherkin、字段表、边界条件清单)。

这篇文章给我最有价值的不是五道关口本身(这是流程设计,懂了能抄),而是**「模型能力是变量,流程设计是常数。变量决定上限,常数决定底线。交易核心系统的底线,不能交给变量」这一句话**。交易系统对稳定性的要求是「可验证、可度量、可负责」,这三件事 LLM 都做不到——LLM 的输出是概率性的、不可重复、不可回溯。流程设计的作用就是把 LLM 装进一个能验证、能度量、能负责的盒子里。

### 三个反直觉的工程判断

1. **「AI Coding = 写代码更快」是错的**。原文数据是「人均增加近 3 倍」,但只算代码行数不算质量成本。真实账要算:代码行数增加 3 倍,但每行代码对应的测试用例、文档、门禁通过率、回滚预案,这些「配套成本」如果不自动化,团队总成本不降反升。**真正的 ROI 来自「流程自动化」而不是「写代码自动化」**。

2. **「TDD 是为了代码质量」是片面的**。原文点出 TDD 在 AI 时代的新价值:**先有一个失败的测试摆在那里,AI 必须让这个测试通过——这是客观的、不可糊弄的锚点**。没有 TDD,AI 的「完成」是主观判断(它自信地说做完了);有 TDD,AI 的「完成」是测试通过(客观可验证)。TDD 不再只是开发方法论,而是**约束 AI 行为的工程基建**。

3. **「门禁检查 = 最后把关」是错的**。原文强调「审核不止在 gate-check,每个阶段产物落地都有对应审核 Agent」。传统流程只在合代码前审一次,改不动的时候已经晚了(架构方向错了,实现再漂亮也要返工)。**门禁是分布式的事前防线,不是单点的最后关口**。

### 但我有 push back：

1. **「五道关口」的认知开销被严重低估**。需求澄清要写 Gherkin、技术方案要五段式、编码要 RED-GREEN、门禁要 9 维度——对一个普通业务需求,光前 2 关就比传统多花 1-2 天。这种重量级流程只适合「资损风险 > X 万元」的核心交易链路,普通 CRUD 业务完全扛不住。**文章没说清楚「五道关口」的适用范围和「轻量版流程」的简化路径**。

2. **「知识库兜底现状」的具体机制没讲**。从知识库拉「现状分析报告」听起来美好,但知识库本身有滞后、不全、过时的问题。AI 拿到一份「3 个月前的现状报告」做的需求澄清,可能比「凭空假设」更糟——会基于错误的事实基础做决策。**知识库的「保鲜期」和「拉取时机」是这套体系成败的关键,文章完全没展开**。

3. **「埋点驱动改进」的因果归因太理想化**。原文说「耗时高 + 对话轮数异常高一定是流程设计问题」,但实际上耗时高可能是:①模型本身慢、②Prompt 不够精简、③工具调用慢、④外部 API 慢、⑤用户思考时间长。光看耗时 + 对话轮数两个指标很难归因。**埋点看板需要更细粒度的归因维度(比如按工具、按阶段、按用户类型分桶),而不是两个聚合指标**。

### 怎么落到 Agent 项目

如果让我基于这篇做一个「AI Coding 流水线插件」(Claude Code / Cursor 通用),5 个模块:

1. **需求澄清 Agent**:接到需求后,先用 LLM 把 PRD 转成 Gherkin 场景(强制业务语言,不出现字段名/接口签名),再从知识库拉相关模块的「现状报告」(代码路径、调用关系、最近变更)作为输入。产出 Spec 文档结构化提交,未通过澄清关口不进入下一阶段。

2. **技术方案 Agent**:接收 Spec 后,按五段式模板(目标/变更位置/字段配置/处理逻辑/阻断兜底)生成方案;从知识库拉「跨环节不变约束」清单,逐条让用户确认纳入或排除(排除需填理由)。未通过方案评审不允许进入编码。

3. **TDD 实施 Agent**:接收方案后,拆成任务列表,每个任务先生成失败测试(对接 Gherkin 场景),跑通 RED 阶段再生成实现代码,跑通 GREEN 阶段才标记任务完成。架构预检在编码前跑一次(防止方向错了再返工)。

4. **门禁卡控 Agent**:三层 DAG 结构——层 1 静态分析(lint / 类型检查)、层 2 业务规则检查(错误码重复 / 新增外部调用 / 关键链路改动)、层 3 集成测试。层内并行、层间串行,任何一层失败阻断 merge。增量代码体检结果发飞书通知。

5. **埋点监控 Agent**:每次需求全流程埋点——耗时(按阶段分桶)、对话轮数、知识库命中率、门禁通过率、回退根因。每天生成日报,异常指标(超出 7 天滑动均值 ± 2σ)自动归因 + 推送改进建议到对应负责人。

**面试答题脚本**:**「AI Coding 我做过最满意的事是把 TDD 从开发方法论变成 AI 行为约束——以前 AI 写完代码说『做完了』,我没法验证;现在我先写一个失败的测试摆在它面前,它必须让这个测试通过才算完成。这个改动把团队的代码合并通过率从 60% 提升到 85%,因为所有合并的代码都已经通过了客观验证,而不是主观宣称。」

## 一句话总结

AI Native 的核心不是「让 AI 写更多代码」,而是「为 AI 重构研发流水线」——把需求变 Gherkin 硬契约、把方案变五段式模板、把编码变 RED-GREEN 强制循环、把门禁变分布式三层 DAG,让 AI 的产出从「主观宣称完成」变成「客观可验证、可度量、可负责」。
