## 原文在说什么

得物技术 (作者：子宸) 写了一篇关于 BP Claw 的文章——这是 FlinkSpec 实时数仓 AI 工程化框架的上游组件。**一句话定义**：BP Claw 是 PM 上游的"AI 数据 BP"，把非标 PRD 自动转成 AI Coding 可消费的高质量需求文档。

**问题定义很尖锐**：AI Coding 效果不稳定，根源不在模型，在输入。同样的框架、不同的需求结果天差地别；需求沟通来回反复；PRD 质量参差不齐导致开发阶段频繁踩雷。文章用一个商业化广告投放案例说明：**流量事件携带多商家 ID（advertiser_id 列表）时，GROUP BY 维度展开方式决定指标口径**——平台侧去重（impression_cnt = 1）vs 商家侧展开（impression_cnt = N），两种 SQL 写法都能跑通，CR 难发现，但下游 CTR/CVR/ROI 系统性失真。**FlinkSpec 的 Flink-SQL Agent 无法自动感知这种"语义正确但口径选择错误"的问题**。

**BP Claw 的介入点是在编码前做"口径显式化"，不是编码后做数据校验。** 结合 OpenViking 知识库（历史建模文档、字段定义、历史踩坑）做语义召回，在进入 FlinkSpec 之前把"必须按平台侧去重"作为强约束写入需求文档。

**三大核心能力：**

1. **智能需求转化**：模拟经验丰富的数据 BP，把 PM 的 PRD 按实时数仓 PRD 七大模块（业务背景 / 角色-页面-指标矩阵 / 指标定义 / 数据流 / 验收标准 / 用数链路 / 风险评估）结构化提取。**核心原则：忠实于原文**——原文有就提取，原文没有就标记 ⚠️ 待补充，原文有歧义就保留 + 标注，**绝不凭空捏造**。
2. **PRD 质量评分**（参照能力）：5 大评分维度。三条核心规则：
   - 技术口径一票否决（< 15 分即使总分 ≥ 90 也标不可执行）
   - 验收标准缺失直接扣 20 分
   - 单维度溢出得分但总分上限 100
3. **自动拉群**：在飞书群 @机器人 + @评审人 + 文档链接 → 自动生成标准化文档 + 质量评估 + 创建评审群 + 邀请成员。"一步触发、全程自动"。

**省 Token 三大技巧：**
- **分段生成策略**：10+ 指标的大文档拆成"骨架 → 每 5 个指标一段 → 验收标准"，每段发送进度反馈，避免上下文溢出。
- **分层调用架构**：编排者模式，把核心逻辑拆分到 3 个独立 Skill（每个独立上下文，避免 Token 膨胀）。
- **模板化 Prompt**：每个模块有严格模板 + Few-Shot 示例约束输出。

**稳定性保障四策略**：忠实性约束 Prompt / 标记机制取代猜测 / 独立评分 Skill 做交叉验证 / 参数校验 + 指数退避重试（2s → 5s → 10s，最多 3 次）。

**关键数据**：PRD 评分每提升 10 分，FlinkSpec 编码阶段效率约提升 30%；PRD ≥ 90 分 Define 阶段一次通过，< 60 分触发技术口径一票否决，频繁 BLOCK-N。

## 我的看法

**我认同的核心点：AI Coding 的瓶颈在输入不在模型。** 这是文章最值钱的判断。多数团队一提 AI Coding 就卷模型、卷 prompt、卷 RAG，BP Claw 反过来从源头 PRD 入手——**再强的模型，喂进去"按商家看曝光数"这种歧义需求，输出也只能二选一猜一个**。把质量门禁前置到需求澄清阶段，比在编码后做数据校验便宜得多。**这是 Spec-Driven Development 在实时数仓的最朴素落地形态**。

**这篇文章给我最有价值的不是 PRD 评分 5 维度，而是"忠实于原文"这条核心原则。** "原文没有就标记待补充，绝不凭空捏造"——这一句话把 AI Coding 的幻觉风险压到了最低。多数 AI Coding 工具会"善意地补全"（看到模糊需求就猜一个），这种"善意"在数仓里是事故源。BP Claw 的做法是"显式承认不知道"，让 PM 来补。这种克制是 AI Coding 工程化的标志。

**三个反直觉的工程判断：**

1. **"PRD 评分不是硬卡点，是参照"是与"BLOCK-N 阻塞协议"并存的设计哲学。** 评分是镜子不是门，BLOCK-N 是真的门。这种"软指标 + 硬指标"组合是健康的质量治理——软指标建立团队质量意识，硬指标守住底线。完全硬卡点会让团队抵触，完全软评分又没约束力。
2. **"技术口径一票否决"是反直觉但极其实用的规则。** 通常评分是总分制，一票否决显得"不公平"。但在数仓场景，没有技术口径的 PRD 等于"AI 不知道按什么粒度 GROUP BY"，下游所有工作都是空中楼阁。这种"局部否决权"是给关键维度加权重的工程化表达。
3. **分段生成 + 进度反馈 > 一次性生成完整文档。** 这不是简单的"避免超时"，而是把"长任务失败成本"从"全部重来"降到"部分损失"。每 5 个指标一段，每段写入后发进度消息让用户知道没卡死。这是分布式系统"幂等 + 部分成功"思想在 AI 应用里的体现。

**但我有 push back：**

1. **PRD 评分 5 维度的权重没说清。** 文章提到技术口径 25 分、验收标准缺失扣 20 分、维度溢出得分上限 100，但其他维度（如业务背景、角色-页面-指标矩阵、数据流、用数链路、风险评估）各自占多少分没说。这种黑盒评分会让评分结果难以复盘——为什么这份 PRD 得了 73 分？哪个维度拖了后腿？需要一份可解释的评分明细。
2. **"参照不是卡点"与"BLOCK-N 阻塞协议"潜在矛盾。** 文章前半段说 BP Claw 的评分"不阻塞流程"，后半段说"< 60 分触发技术口径一票否决，FlinkSpec Define 阶段频繁 BLOCK-N"。到底评分会不会触发流程阻塞？如果不会，BLOCK-N 是谁触发的？如果会，"参照不是卡点"就站不住脚。这个边界没明确。
3. **长 PRD 分段生成的失败语义没定义。** "先建骨架 → 逐段追加 → 追加失败"的情况下，骨架是否保留？已追加的段落是否回滚？用户看到的是半成品还是完整文档？分段的好处是"失败不从头来"，但前提是"失败有定义好的回滚策略"，这块没说。

### 怎么落到 Agent 项目

如果让我基于这篇做一个"AI Coding 需求澄清 Agent"项目，我会拆成五个模块：

1. **PRD 模板仓库**：实时数仓 PRD 七大模块的标准化模板 + Few-Shot 示例，进 Git 管理；支持版本化和复用。
2. **需求转化 Agent**：模拟数据 BP 工作流，按"忠实于原文"原则做结构化提取，未知项标记 ⚠️ 待补充；禁止凭空捏造。
3. **质量评分 Agent**：5 维度可解释评分，输出维度明细 + 改进建议；技术口径维度带一票否决权。
4. **OpenViking 知识库召回**：基于历史建模文档、字段定义、踩坑记录做语义召回，把"历史已决策的口径"作为强约束注入当前 PRD。
5. **飞书集成 + 自动拉群**：@机器人 + 文档链接触发，自动生成标准化文档 + 评分报告 + 评审群邀请；分段生成时实时反馈进度。

面试时的回答脚本："我做过一个 AI Coding 需求澄清的项目，核心洞察是 AI Coding 的瓶颈在输入不在模型。我们做了一个 AI 数据 BP，把 PM 的非标 PRD 自动转成结构化文档 + 质量评分。评分是参照不是卡点，但技术口径维度一票否决——没有技术口径 AI Coding 根本启不动。最关键的原则是'忠实于原文'：原文有就提取，原文没有就标记待补充，绝不凭空捏造。结果是 PRD 评分每提升 10 分，编码效率约提升 30%。"

## 一句话总结

AI Coding 提效的天花板由输入决定——再强的模型也救不了一份"按商家看曝光"这种歧义 PRD，把质量门禁前置到需求澄清阶段是真正的杠杆点。

## 附录：BP Claw 三大核心能力的工程细节（面试素材）

### 能力一：智能需求转化（核心）
- 七大模块覆盖：业务背景 / 角色-页面-指标矩阵 / 指标定义 / 数据流 / 验收标准 / 用数链路 / 风险评估。
- PM 提交的原始 PRD 通常只覆盖 2-3 个模块。
- 转化原则"忠实于原文"：原文有 → 结构化提取；原文没有 → 标记 ⚠️ 待补充；原文有歧义 → 保留 + 标注；原文划删除线 → 标注"本期不纳入"。

### 能力二：PRD 质量评分（参照）
- 5 大评分维度（具体权重未公开）。
- 三条核心规则：技术口径一票否决（< 15 分即使总分 ≥ 90 也标不可执行）；验收标准缺失扣 20 分（严重不足 ≤ 5 分扣 10 分）；单维度溢出得分但总分上限 100。
- 关键数据：每提升 10 分 → FlinkSpec 编码效率提升 30%；≥ 90 分 → Define 阶段一次通过、整体交付天级；< 60 分 → 触发技术口径一票否决、整体交付周级。

### 能力三：自动拉群（工作流融合）
- 触发方式：飞书群里 @机器人 + @评审人 + 文档链接。
- 自动执行：读取文档 → 生成标准化文档 → 质量评估 → 创建评审群 → 邀请成员 → 发送文档和诊断报告。
- 等待时长：1-5 分钟。

## 附录：省 Token 三大技巧

1. **分段生成策略**：10+ 指标的大文档拆成"骨架 → 每 5 个指标一段 → 验收标准"，每段发送进度反馈。
2. **分层调用架构**：编排者模式，核心逻辑拆分到 3 个独立 Skill，每个独立上下文避免 Token 膨胀。
3. **模板化 Prompt**：每个模块严格模板 + Markdown 表格约束结构 + Few-Shot 示例引导输出风格。

## 附录：稳定性保障四策略

1. **忠实性约束 Prompt**：多层约束（原文有 → 提取；原文没有 → 标记；绝不发明；绝不猜测）。
2. **标记机制取代猜测**：明确标记待补充 + 说明缺失内容 + 给出建议补充方向。
3. **质量评分交叉验证**：prd-quality-scorer 作为独立 Skill 做第二遍审查。
4. **参数校验 + 重试**：飞书 API 调用前强制校验必填参数；生成失败 → 最多重试 3 次（2s → 5s → 10s 指数退避）；3 次失败 → 终止 + 错误消息；绝不降级生成"简化版"。
