## 原文在说什么

得物这篇讲的是企业知识问答 Agent 的工程现实——一个回答要准确，需要查得全（召回率）、查得准（精准度）、理解得对（多模态）、看得对（权限隔离）。这些能力不是堆功能能做出来的，需要一个强大的 Agent 运行时做底座。

作者选了 **AgentScope 2.0 的 HarnessAgent**——面向生产环境的 Agent 实现，内置 ReAct 循环、Middleware、长期记忆、子 Agent 编排、沙箱隔离。文章重点用了三个能力：HarnessAgent 架构、Middleware 机制、并行工具调用。

**Agent 自主决策的复合检索架构**——传统 RAG 是单向流程（用户提问 → 向量检索 → 拼接上下文 → 生成回答），Agent 是被动的——检索到什么就用什么，不会判断信息是否充分。

本文的流程完全不同，核心是 **Agent 的决策权**：每轮都是"搜索 → 评估 → 决策"闭环，Agent 自己决定用哪些工具、搜几次、是否需要精读、什么时候停止。用户不需要告诉 Agent"你去查飞书文档"，Agent 自己知道什么时候该查。

**多源并行检索**——四条数据源：企业知识库 + 飞书文档 + 飞书消息 + 飞书妙记。一次推理中决定调用多个工具时，框架自动并行执行（Toolkit.parallel(true) + Java 21 Virtual Thread）。

**权限隔离两层**——知识库按业务领域/部门划分，飞书生态通过 UserCallContext 注入用户 openId。同一问题不同用户看到不同结果。

**自主决策的三种挖掘策略**——拿到第一轮检索结果后，Agent 基于结构化提示词中的策略进行多维度评估：
- **直接整合**：信息足够，直接进入整合阶段
- **深挖**（同源）：用同一个工具换关键词或精读
- **切换源**：当前源不给力，切到其他源

**决策依据：结构化提示词 + Middleware 兜底**——AGENTS.md 不是指令列表，是完整的决策流程图。结构化提示词负责"做什么"（策略框架），Middleware 负责"做得好"（质量保障），ReAct 循环负责"怎么做"（执行流程）。三者各司其职。

**信息整合能力三个层面**：
1. 多角度并行搜索，最大化召回（旧版废弃 vs 新版最新）
2. 从搜索到精读，深挖关键文档（向量检索只返回片段，全文藏在其他段落）
3. 多源交叉验证，有判断力的信息整合（官方文档 > 会议纪要，冲突时标注让用户判断）

**三阶段质量 Pipeline**——核心思路是"召回靠查询扩展，精准靠三阶段 Pipeline"：
- **Stage 0: FastPass**——结果数 ≤ 2 且原始 score ≥ 0.7 → 直接透传，零延迟
- **Stage 1: Reranker 粗筛**——交叉编码器重新打分，过滤"词像但意思不对"的结果（gte-rerank-v2，阈值 0.3，Top-8）
- **Stage 2: LLM Grading 精评**——大模型逐条打分（0.1~1.0 四级），过滤"主题对但不够直接"的结果（阈值 0.5）

通过 AgentScope Middleware 在 `onActing` 钩子拦截 `knowledge_search` 工具结果，过滤对 Agent 完全透明。

**查询扩展：自然语言句子而非关键词**——Embedding 模型在自然语言文本上训练，"一句话"的语义编码远比"一串词"精准。用户问"怎么申请加薪"，关键词"加薪 申请 流程 条件"缺乏语法结构，自然语言变体"得物内部员工申请薪资调整的流程是什么"有完整主谓宾。

**多模态：图片全生命周期管理**——用户上传图片后系统检测上下文，自动切换视觉模型。校验不仅查本轮，还查历史对话——大模型无状态，历史图片每轮都要重发。

**生产级可靠性：多实例 SSE 断点续传三种路径**：
1. **同实例恢复**（最常见，页面刷新/切后台/网络闪断）：本地内存仍有 Agent 状态，直接发快照恢复
2. **跨实例转发**（负载均衡分到另一实例）：通过 Redis 路由表查到原实例，内部 HTTP 转发
3. **快照重建兜底**（原实例宕机）：从 Redis 重建完整会话

**关键设计决策**：
- **快照一帧恢复 vs 逐条重放**：早期"按顺序重发所有事件"，多轮 Agent 对话可能几百事件，前端会合并跳变。快照方案折叠成"当前状态"，像游戏存档一帧恢复
- **路由表 + 内部转发 vs Redis Pub/Sub**：Pub/Sub 致命问题——订阅生效有延迟，新订阅者连上时已错过前面消息。方案核心：Redis 只存路由信息，不参与事件推送

**核心创新点（与"标准 RAG 套壳"的六项差异）**：
- 复合检索不是"多搜几个地方"——Agent 自主选源组合，搜索和精读交替推进
- 质量 Pipeline 不只是 Reranker——三级：FastPass / Reranker / LLM Grading
- SSE 断点续传不靠 Pub/Sub——路由表 + 内部转发

## 我的看法

我认同作者把"HarnessAgent + Middleware + 三阶段 Pipeline"作为知识问答 Agent 工程起点的判断。这篇文章给我最有价值的不是某个具体技术，而是几个反直觉的工程判断：

第一，**Agent 决策权比"AI 检索结果"更值得设计**。传统 RAG 思路是"我（工程师）设计检索流程，AI 被动执行"，所以质量上限被工程师能力封死。本文做法是反过来的——工程师只画"决策框架"（AGENTS.md），让 Agent 自己决定用什么工具、搜几次、什么时候停。**Agent 决策权是 AI 应用的灵魂，没有决策权的产品只是流程自动化，不是 Agent**。

第二，**Middleware 机制是把"质量控制"和"业务逻辑"解耦的关键**。三阶段 Pipeline 不是写死在 Agent 代码里，而是通过 Middleware 在 `onActing` 钩子拦截工具结果——调阈值、切 Reranker 模型、开关 LLM Grading 都改配置不改代码。**这是软件工程"横切关注点"范式应用到 LLM 场景，跟 AOP、Filter、Interceptor 是同一个套路**。

第三，**快照一帧恢复比逐条重放更工程化**。"把所有历史事件按顺序重新发送"听起来自然，但前端会合并跳变。快照方案把所有事件折叠成"当前状态"一帧恢复——像游戏存档。这个判断在分布式系统里就是"状态机恢复 vs 日志重放"的经典选择：**状态机恢复更快但需要快照，日志重放更慢但更通用**。

但我有 push back：

第一，**LLM Grading 的成本没说**。Stage 2 用大模型逐条打分——一条结果一次 LLM 调用，10 条结果就是 10 次。Stage 2 的 Token 成本和延迟是 Stage 1（Reranker）的几十倍。文章没说 Stage 2 的实际命中率和成本权衡——是必须的还是可选的？

第二，**三阶段 Pipeline 的 Stage 0 阈值（size ≤ 2 且 score ≥ 0.7）是经验值，不是工程化结论**。这个数字怎么来的？是大量实验调出来的还是拍脑袋的？阈值漂移怎么办？文章没说监控和回滚机制。

第三，**多源并行检索的"并行"是有上限的**。Toolkit.parallel(true) + Virtual Thread 是技术实现，但同时调用 4 个工具意味着 4 倍的并发成本（飞书 API 限流、知识库查询压力）。文章没说并发上限和降级策略。

### 怎么落到 Agent 项目

核心模块五件套：**HarnessAgent 基座、结构化 AGENTS.md、Middleware 质量 Pipeline、并行工具调度、SSE 三路径恢复**。

1. **HarnessAgent 基座**：选一个成熟 Agent 框架（AgentScope 2.0 / LangGraph / Spring AI Alibaba），**不要重新发明轮子**。重点考察：ReAct 循环、Middleware、长期记忆、并行工具调用。
2. **结构化 AGENTS.md**：决策框架，不是指令列表——告诉 Agent 做什么和为什么，不告诉怎么做。
3. **Middleware 质量 Pipeline**：横切关注点统一处理（质量过滤、限流、监控、审计），业务逻辑和工程化逻辑解耦。
4. **并行工具调度**：I/O 密集型工具（HTTP/API）自动并行，CPU 密集型串行；并发上限和降级策略必备。
5. **SSE 三路径恢复**：同实例本地状态 → 跨实例路由转发 → 快照重建兜底。Redis 只存路由不存事件。

**面试时被问"RAG 怎么从套壳变成工程化产品"**——直接答"Agent 自主决策 + Middleware 质量控制 + SSE 多实例恢复"。**真正的工程能力不在 RAG 本身**，而在于：决策权怎么给 Agent、Middleware 怎么设计质量策略、生产可靠性怎么兜底——把这三件事做出来，知识问答 Agent 才从"AI 套壳"变成"可治理生产系统"。

## 一句话总结

知识问答 Agent 的关键不是 RAG 本身，而是把 Agent 决策权、Middleware 质量控制、SSE 多实例恢复这三件事做出来——Agent 自主决策替代预设流程，Middleware 横切关注点分离质量策略，多实例三路径恢复兜底生产可靠性。
