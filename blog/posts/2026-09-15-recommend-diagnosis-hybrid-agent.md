## 原文在说什么

得物这篇讲推荐系统诊断的工程现实——"召回→粗排→精排→策略过滤"多层嵌套逻辑里，每个 `filter_code` 或异常分值都是待解的谜题。过去排查高度依赖个人经验甚至多方会诊，是低效重复的体力消耗。

"推查查"是得物做的推荐系统诊断 Agent，目标是把黑盒推荐系统变成**白盒可追踪、可预测**。作者深度权衡后选了 OpenClaw（不是通用开源框架定制），理由是"工程确定性"——打通智能诊断"生产环境落地"的最后一公里。

**核心架构是 Highway & ATV 双轨混合智能体**——拒绝在"极致响应的线性逻辑"和"深度推理的自主智能"间二选一，**两条路都要**。中间是**智能调度器（判定引擎）**：用户问题一来先去知识库快速匹配，命中标准 Story 走 Highway；匹配不上或 Highway 执行中卡住，立刻切换到 ATV 模式。

**Story 基座**——基于内部 API 沉淀的 MCP 标准 Skill 工具集（因数据安全问题不上传公司 Skill 库）。这些 Skill 就像乐高积木，Highway 剧本可以按顺序拼，ATV 推理引擎可以按需调用。**新增排查能力？再封装一个 Skill 加入即可，热插拔，不用停机**。

**Highway Story 编排**——把专家排查路径固化成可复用的标准剧本。每个 Story 本质是有序的 Skill 编排模板：

```
Story: 商品推荐异常-标准诊断
├── Step 1: screenshot-trace-query     # 截图识别，自动匹配Trace
├── Step 2: user-profile-query         # 查用户购买/点击历史
├── Step 3: layer-items-query          # 看商品在各层曝光情况
├── Step 4: strategy-logs-query        # 核对策略干预（去重/过滤）
├── Step 5: commodity-forward-query    # 查商品正排信息
└── Step 6: output_diagnosis           # 输出诊断结论
```

**Story 的精髓**——把专家脑海里的"经验"变成可执行、可复用、可进化的标准化剧本。

**ATV ReAct 循环**——OpenClaw 框架实现的经典推理-行动-观察循环，处理 Highway 解决不了的复杂异常场景。

## 我的看法

我认同作者把"Highway & ATV 双轨"作为诊断 Agent 架构起点的判断。这篇文章给我最有价值的不是架构本身，而是几个反直觉的工程判断：

第一，**不要在"快路径"和"慢路径"之间二选一**。常见误区是要么追求极致响应（写死流程、不灵活）、要么追求深度推理（每次都让 LLM 想一遍、慢且贵）。双轨架构用调度器分流——**90% 的常见问题走 Highway 快路径（成本低、响应快），10% 的复杂异常走 ATV 慢路径（深度推理、能解决新问题）**。这跟 CDN 边缘计算 + 中心计算的思路一样。

第二，**Story = Skill 编排模板**是非常聪明的工程抽象。Skill 是原子能力（查用户画像、查商品曝光），Story 是组合这些能力的剧本——这跟微服务 + 工作流编排（BPMN）是同一个范式。**专家经验不再藏在脑子里，而是变成可执行的 JSON/YAML 模板**。

第三，**不上传 Skill 库**反映数据安全意识。推荐系统的内部 API 涉及用户行为数据、商业策略，**不能因为"便于共享"就泄露到公网 Skill 库**。这是工程素养的具体体现。

但我有 push back：

第一，**调度器的判定标准没说清**。用户问题怎么匹配 Story？关键词？语义相似度？规则？这决定了 Highway 命中率，进而影响整个系统的效率。文章没说这块怎么设计。

第二，**Story 的演化机制没说**。专家经验会过时，Story 模板怎么更新？谁来更新？怎么 A/B 测试新 Story？

第三，**ATV ReAct 循环的"卡住"判定没说**。Highway 执行中"卡住"的判定是什么？是工具超时？还是中间步骤失败？这个判定边界不清晰会导致模式切换过于频繁或过于迟钝。

### 怎么落到 Agent 项目

核心模块五件套：**Skill 注册中心、Story 模板库、智能调度器、ATV ReAct 引擎、Skill 热插拔**。

1. **Skill 注册中心**：原子能力 + MCP 标准化接口——可热插拔
2. **Story 模板库**：Skill 编排模板（JSON/YAML），专家经验沉淀
3. **智能调度器**：用户问题匹配 Story，命中走 Highway；否则或失败时切 ATV
4. **ATV ReAct 引擎**：处理长尾复杂问题
5. **Skill 热插拔**：不停机添加新能力

**面试时被问"AI 怎么落地到运维/诊断场景"**——直接答"Highway 快路径 + ATV 慢路径 + 调度器分流"。**真正的工程能力不在双轨架构本身**，而在于：调度器判定标准、Story 演化机制、ATV 卡住判定——把这三件事做出来，诊断 Agent 才从 demo 变成可治理产品。

## 一句话总结

不要在快路径和慢路径之间二选一——用调度器分流，90% 的常见问题走确定性 Story、10% 的复杂异常走 ReAct 推理，平衡效率与深度是工程设计的核心。
