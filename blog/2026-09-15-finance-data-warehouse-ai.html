财务数仓 AI 全链路增强，但真正难的是 L3 级人机协作的边界划法

2026-09-15 · 数据仓库 AI Coding 财务数仓 LLM 应用

读文笔记。本文是对他人文章的摘要与评述，非原文转载。 原文：财务数仓 Claude AI Coding 应用实战｜得物技术 · 得物技术

原文在说什么

得物技术 (作者：丹克) 写了一篇关于财务数仓场景下 Claude AI Coding 的实战长文。立论起点很清晰：财务域是电商数仓里复杂度最高、容错率最低的领域——字段间有严格数学公式（正向 - 冲销 = 冲销之后）、业务规则涉及跨周期分摊、指标多口径（业务口径 / 资金口径 / 财管报口径）。

核心方法论三条：

  1. 规范即 Prompt：把沉淀的规范文档（命名规则 DWD/DIM/DWS/ADM、时间周期 1d/7d/30d/wtd/mtd/ytd、刷新周期、字段命名原则 {主体}{业务场景}{币种}{度量}{时间单位}）作为 AI 输入的核心，规范质量 = AI 输出质量。
  2. 迭代是常态：不期待一次出完美结果，每次迭代重点验证复杂字段（条件取值、分摊、冲销、多口径），迭代产物不只是修正输出，更重要的是完善规范文档。
  3. 海量文件阅读：利用超大 Context 把历史文档、设计链路表、代码一次性灌入模型，模型输出思路供数仓工程师整理，特别是画业务架构图。

四个落地场景：

  • AI OneData 标准化建模：财务核算项目涉及百张以上表、十余个业务过程、数百个指标。AI 按 ODS→DWD/DIM→DWS→ADM 分层输出建模建议，反复迭代。
  • AI SQL Coding（财务 UE 表迭代）：AI 把 PRD 提炼为结构化要点，自动生成待确认问题清单；输出符合规范的 DDL 和 SELECT；处理窗口函数、多层嵌套、存量长 SQL 重构。
  • AI 数据测试（财务 UE 表邮费迭代）：测试用例覆盖度提升、复杂逻辑逐步分析找 Bug、上下游影响分析、公式验证与精度问题诊断。
  • AI 需求文档转化：通过飞书 MCP 让 Cursor 直接读取 BI 文档，自动总结两张表（DWS/ADS）各自要改什么，节省碎片化沟通时间。

人机协作分级：借用自动驾驶分级，把数仓大模型应用分 L1-L5，当前处于 L2 向 L3 过渡阶段——在明确 Prompt 约束和规范文档支撑下，AI 能接管绝大部分标准化的执行动作，但业务判断仍由人做。分工逻辑是：规范执行是 AI 长板、业务判断是 AI 短板。

我的看法

我认同的核心点：规范即 Prompt，把规范文档当一等公民对待。 这跟上一篇 Galaxy MCP 文章里”规范化 I/O”是一脉相承的判断。AI 输出质量 = 规范质量 × 模型能力，规范跟不上，模型再强也是 garbage in garbage out。真正值钱的不是”哪个 prompt 写得好”，而是”团队有没有一套活文档化的规范”。这跟软件工程里”代码即文档”是反的——AI Coding 时代是”规范即代码”。

这篇文章给我最有价值的不是 4 个场景的提效数据，而是”AI 输出要反过来迭代规范文档”这个反向闭环。 这是少数把 AI 应用从”工具使用”提升到”系统演进”的洞察。多数团队用 AI 是”用完就完了”，作者强调”每次迭代的产物不只是修正后的输出，更重要的是规范文档的完善”——这是把 AI 当成”团队规范的探测器”，哪里 AI 出错多就说明规范有缺口。这种用法比单纯提效有更长期的价值。

三个反直觉的工程判断：

  1. 财务数仓的 AI 价值在”跨周期分摊”和”多口径指标”这种最难的地方，反而不是”DDL 生成”。 因为前者要求对业务理解深、容易出错、规范难写完整，所以 AI 提效带来的边际收益最大。简单 DDL 模板化本来就是体力活，AI 提效有限。这反向论证了”AI 在规范完善的高难度领域价值最大”。
  2. AI 测试 SQL 比 AI 写 SQL 更值钱。 测试用例设计的”覆盖度”和”边界发现”是个人能力差异最大的地方，AI 能从规则理解层面补充人容易忽略的测试点（如抽样验证、精度验证）。这跟传统认知相反——多数人以为 AI 提效主要在编码，不在测试。
  3. “海量文件阅读”是 LLM 时代数仓工程师的新基本功。 把历史文档、表结构、代码一次性灌入模型，让模型输出业务架构图思路，本质上是用 LLM 的超大 Context 替代人类”读代码理解业务”的体力活。这把数仓工程师从”读代码的人”解放成”画架构图的人”。

但我有 push back：

  1. “L3 时刻”比喻不严谨。 自动驾驶 L3 是”有条件自动驾驶，系统能在特定场景下完全负责，但人需要准备接管”。文章说”AI 能接管绝大部分标准化的执行动作”——这跟 L3 不完全对应，因为数仓场景里 AI 失误的代价（数据错误）远比自动驾驶失误的代价可控性差。L3 是系统负责 + 人兜底，数仓更像是 L2（人主导 + AI 辅助）。这个分级用得不够精确，会误导团队对 AI 能力的预期。
  2. 规范文档的演进机制没说清。 既然每次迭代反过来完善规范，那”规范文档”由谁来维护？AI 自己改规范会不会出问题？规范版本怎么管理？规范改了 AI 怎么感知？这些治理问题没提。实际工程里，规范文档一旦失去”权威地位”就会迅速腐烂。
  3. “AI 测试的问题发现能力提升”缺少对照实验。 文章说 AI 能”发现人工难以发现的逻辑错误、识别精度问题并区分可接受的误差”，但没有数据支撑（多少测试用例是 AI 单独发现的、误报率多少、跟纯人工测试的对比）。这是 PR 表述还是真实数据，作为面试者会追问。

怎么落到 Agent 项目

如果让我基于这篇做一个”财务数仓 AI 助手”项目，我会拆成五个模块：

  1. 规范仓库 + 版本控制：把所有数仓规范（命名、时间周期、字段命名、指标口径）作为结构化 Markdown 入 Git，建立规范变更的 PR Review 流程。
  2. OneData 建模 Agent：基于规范和历史表结构，输出 ODS→DWD/DWS→ADM 的建模建议，重点处理多口径指标和跨周期分摊字段。
  3. SQL Coding Agent：基于 PRD + 规范生成 DDL 和 SELECT，对存量长 SQL 做分段重构和注释补充，输出符合规范的代码。
  4. 测试 SQL Agent：基于 PRD + 业务规则 + 上下游依赖，生成覆盖度更全的测试 SQL，重点补充人工容易忽略的边界场景（抽样、精度、跨周期）。
  5. 需求文档 Agent：通过飞书 MCP 读取 BI 文档，自动总结每张表的改动点和待确认问题，反向触发规范文档的更新 PR。

面试时的回答脚本：“我做过一个财务数仓 AI 助手项目，核心是规范即 Prompt，把数仓规范文档当一等公民进 Git 管理。AI 用在四个环节：OneData 建模、SQL Coding、数据测试、需求文档转化。最关键的洞察是：AI 输出的错误反向暴露规范的缺口，每次迭代反过来完善规范文档，让 AI 成为团队规范的’探测器’。分工上，规范执行交给 AI，业务判断保留给人——AI 擅长守规范，人擅长理解业务。”

一句话总结

财务数仓 AI 的真正价值不是”AI 写 SQL 快了”，而是把 AI 用成团队规范的”压力测试器”——AI 哪里反复出错，就说明规范哪里需要补。

附录：财务数仓的特殊挑战（面试素材）

  • 字段数学公式严格：正向 - 冲销 = 冲销之后；子项相加 = 汇总项；任意一项改动要验证几十个相关字段。
  • 跨周期分摊：订单时间与收入确认时间不匹配（如商业化订单 vs 交易订单），分摊逻辑难验证。
  • 多口径指标：业务口径 / 资金口径 / 财管报口径，同一指标有多种实现路径。
  • 横向域依赖：财务与核算域、技术成本域、促销补贴域、商业化域、分析域都交叉。
  • 命名规范严格：{主体}{业务场景}{币种标识}{度量类型}{时间单位}，人工遵守率随交付压力下降。
  • OneData 规模：仅财务核算项目首轮就涉及百张以上表、十余个业务过程、数百个指标。

附录：AI 测试 SQL 的 5 类提效（实战细节）

  1. 测试 SQL 生成效率：从提出测试要求到生成完整 SQL，时间大幅缩短。
  2. 测试用例覆盖度：AI 从规则理解层面补充人容易忽略的测试点（如抽样验证、精度验证、跨周期分摊场景）。
  3. 复杂逻辑逐步分析：邮费冲销逻辑中 AI 能逐步分析退小仓场景下的多种分支情况，识别逻辑漏洞。
  4. 上下游影响分析：一个字段改动自动分析对上下游的影响，识别需同步验证的相关字段。
  5. 公式验证与精度诊断：AI 自动生成公式验证 SQL，区分真正的逻辑错误和可接受的精度误差，避免误报。

附录：财务数仓 AI 落地的”反向闭环”模式

这是文章里最值钱的工程洞察，跟多数团队的”AI 用完就完了”完全相反。完整闭环是：

规范文档（结构化 Markdown 入 Git）
    ↓
原始数据 + 表结构灌入模型
    ↓
AI 输出建模建议 / SQL / 测试用例
    ↓
数仓工程师验证（重点验证复杂字段）
    ↓
发现 AI 输出错误 → 不是"修 AI"，而是"修规范"
    ↓
规范文档 PR 更新（标注 Owner + 变更原因）
    ↓
规范变了 → 后续所有 AI 输出自动遵循新规范

关键反直觉点：AI 出错不是 AI 的问题，是规范的缺口。团队应该把”AI 反复出错的地方”当作”规范需要补的清单”。这种用法把 AI 从”工具”变成”团队规范的探测器”——哪里 AI 反复出错，就说明团队规范哪里有缺口。

这种模式特别适合规范本身在快速演进的场景（财务、业务运营、推荐系统）。规范稳定的场景（底层 ETL）用 SDD + Spec-to-Code 更划算，规范不稳定的场景用”反向闭环”迭代更划算。
