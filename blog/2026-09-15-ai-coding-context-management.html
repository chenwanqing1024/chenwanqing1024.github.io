AI 编码真正的瓶颈：上下文管理失效 — 读《Claude Code + OpenSpec》

2026-09-15 · 上下文工程 Claude Code OpenSpec SDD规格驱动 MCP Auto Memory

读文笔记。本文是对他人文章的摘要与评述，非原文转载。 原文：Claude Code + OpenSpec 正在加速 AICoding 落地：从模型博弈到工程化的范式转移｜得物技术 · 得物技术

原文在说什么

得物技术（作者后羿）从行业高度重新审视 AI 编码的核心瓶颈 — 不是模型不够强，而是上下文管理失效。

一、生产力悖论与认知负荷。 开发者主观感知 AI 让速度提升 20%，但实际完成任务时间反而增加 19%。根源是 AI 在长上下文中的效能衰减 + Fix/Test 修正循环 + 需要更多人工干预。引用 DORA 2024 报告：AI 采用率每增加 25%，交付稳定性反而下降 7.2%。

二、上下文断崖。 GPT-4o 在 1K Token 准确率 99.3%，扩展到 32K Token 时暴跌至 69.7%。这说明单纯扩大上下文窗口不能解决问题。两个核心概念：(1) Context Poisoning（上下文中毒） — 对话历史过长或含过多无关代码时性能非线性下降；(2) Attention Drift（注意力漂移） — 偏离任务核心关注。

三、上下文工程的兴起。 上下文工程（Context Engineering）正在取代提示词工程（Prompt Engineering）。核心不是”如何写更好的指令”，而是”如何为模型筛选最精准的 Token 集合”。在大型组织中，关键决策散落在飞书文档评论、群消息、会议中 — AI 缺乏这些 Implicit Knowledge，生成的方案虽符合语法但违背架构初衷。

四、上下文作为一等系统。 现代 AI 代理架构将上下文视为具有自身架构、生命周期和约束的”一等系统”，不再是字符串拼接，而是精密的”编译器管道”。

五、Claude Code 的核心机制。 - 代理循环（Agentic Loop）：模仿人类工程师的”收集—行动—验证”闭环。 - 终端原生 + Unix 哲学：支持 Pipe、CI/CD 集成（GitHub Actions 自动 Code Review）。 - MCP + 按需加载：不一次性加载所有 API 定义，而是通过代码执行按需调用 MCP 服务（如分析大型数据库时编写针对性查询，仅将结果摘要读入上下文）。 - CLAUDE.md：根目录的”操作手册”，存储项目特定编码标准/架构决策/测试指令，提供持久、跨会话约束。 - Auto Memory：自动在 MEMORY.md 记录构建命令、调试心得、用户偏好；新会话加载前 200 行。

六、OpenSpec — 规格驱动开发（SDD）。 核心理念：在写任何代码之前，先由人类与 AI 共同协商并锁定一份机器可读、人可评审的规格文档。SDD 三阶段演进：自然语言规格 → 结构化文档规格 → OpenSpec 等机器可执行规格。OpenSpec 工件体系：每个变更（Change）组织在独立文件夹，包含 proposal.md / specs/ / tasks.md / design.md。

七、OpenSpec 的关键设计 — 归档（Archive）机制。 AI 处理新任务最忌讳被旧任务的陈旧信息干扰。OpenSpec 在任务完成后执行 /opsx:archive 把临时规格归档为 openspec/specs/ 下的永久规格，下一次新 AI 代理（或新员工）只需读取这份规格即可获得完整业务语境。

八、实战案例 — 重构优惠券结算逻辑。 四步流程：(1) /opsx:propose 生成骨架；(2) 审阅 spec.md，补全”过期临界点并发问题 + Lua 脚本原子性”等场景；(3) /opsx:apply 受控执行，对照 tasks.md 逐项实施，跑测试失败自动修复；(4) /opsx:archive 沉淀为标准规格。

九、角色转变。 软件工程师从”码农”变成”规格定义者”。如果 AI 能根据完美描述生成任何代码，那么”代码”本身变成编译中间产物，“规格”才是核心产品。

十、效能飞轮。 成功落地需要建立正向循环 — 个人使用 Skill 沉淀经验 → 团队共享 Skill 库 → 团队 AI 编码能力提升 → 更多经验沉淀 → 飞轮加速旋转。从”个人技能”到”组织技能”的迁移路径，正是 AI 编码落地的高级形态。

我的看法

我认同： 文章最核心的反共识判断是 “AI 编码的瓶颈从来不是模型不够聪明，而是我们与 AI 之间的沟通带宽太低且上下文太脏”。这句话精准描述了 2026 年 AI 落地的真实状态 — 模型能力溢出，工程能力不足。

这篇文章给我最有价值的不是 X，而是 Y： 不是 OpenSpec 工件体系本身（任何 spec 工具都能实现），而是 “归档（Archive）作为知识沉淀机制”。这是把”AI 生成的临时规格”升级为”团队长期记忆”的关键 — 否则每次会话都从零开始。

反直觉的工程判断：

  1. DORA 报告里 7.2% 的稳定性下降是 AI 编码的隐藏税。 大家都说 AI 提升效率，但 DORA 数据显示采用 AI 越多反而交付越不稳定。这不是模型的错，是没有上下文工程的错 — 你让 AI 在模糊需求下暴力生成代码，bug 率自然上升。

  2. CLAUDE.md + Auto Memory 是 OpenSpec 之前的过渡方案。 OpenSpec 才是终局 — 规格作为一等公民，所有 Agent 共享。但 OpenSpec 的学习成本高、对存量项目改造成本大。对于已有项目，CLAUDE.md 是”半步”；对于新项目，OpenSpec 才是”一步到位”。

  3. MCP 的”按需加载”比工具数量更重要。 一开始 MCP 工具接入越多越好，但工具定义本身会撑爆上下文。Claude Code 的”代码执行”模式（让 Agent 编写代码按需调用 MCP）才是关键 — 这避免了”工具菜单爆炸”问题。

但我有 push back：

  1. 99.3% → 69.7% 的断崖数据被过度简化。 文章引用 GPT-4o 数据，但没区分”模型类型” — GPT-4o 在 1K 到 32K 的衰减，与 Claude/Gemini 不同（Claude 的长上下文衰减更平滑）。不同模型的”上下文工程最优策略”不一样，不能一概而论。

  2. SDD 的隐性成本被低估。 OpenSpec 的工件体系（proposal.md/specs/tasks.md/design.md）听起来很优雅，但每个变更都要走完这四个文档的维护，对一个 5 人小团队的小迭代来说成本可能超过价值。文章没给出”什么规模的团队/项目适合 SDD”的判断标准。

  3. “代码是中间产物，规格是核心产品”过于理想。 现实里规格也会过期、也会和实现偏离。OpenSpec 的归档机制虽然能沉淀，但规格本身的版本管理、与代码的对齐（specs 和代码不一致时信谁？）才是真正的难题。文章没提 spec drift 的检测和修复机制。

怎么落到 Agent 项目

假设让我基于这篇做一个“上下文工程平台（Context Engineering Platform）”，会拆成五个模块：

  1. 上下文采集器：从飞书文档 / Git 历史 / 会议纪要 / 代码注释 / 群消息中提取 Implicit Knowledge，构建组织级知识图谱。
  2. Token 精准筛选器：根据当前任务从知识图谱中检索最相关的 Top-K 上下文（不是全量），用 embedding + rerank 双阶段。
  3. CLAUDE.md + Auto Memory 持久化层：把项目级约束存为 Markdown + 自动从会话中提炼”调试心得”沉淀到 MEMORY.md。
  4. OpenSpec 风格的 SDD 工作流：每个需求走 proposal → spec → tasks → archive 四阶段，规格和代码双向链接（类似 GitHub Issues → PR 闭环）。
  5. 上下文健康度看板：监控 DORA 指标（部署频率 / 变更前置时间 / 变更失败率 / 恢复时间）的 AI 影响系数，主动预警”上下文过载”任务。

面试回答脚本：”AI 编码最大的瓶颈是上下文管理，不是模型。我在做的 Context Engineering Platform，核心是把’散落的组织知识’按 SDD 流程结构化，让每个 AI 任务拿到的不是全量上下文，而是最精准的 Top-K Token — DORA 的 7.2% 稳定性下降就是这种’上下文过载’的代价。”

与得物文章方法论的延伸： 作者强调”上下文工程取代提示词工程”是行业范式转移。我再加一层视角：Spec Engineering（规格工程）正在取代上下文工程。当 OpenSpec 之类的工具把”规格”作为一等公民后，开发者的核心能力不再是”写好 prompt”，而是”写好 spec”。这是从”沟通带宽”到”协议标准化”的进一步跃迁。

一句话总结

AI 编码的瓶颈不在模型能力（99.3% → 69.7% 的断崖说明扩展窗口无效），而在上下文工程 — 用 SDD 规格驱动 + CLAUDE.md 持久化 + MCP 按需加载 + Auto Memory 归档，让 AI 拿到”最精准的 Token 集合”而不是全量历史。

给架构师的延伸： DORA 报告里”AI 采用率 +25% → 稳定性下降 7.2%“这个数据，最值得警惕的不是数字本身，而是AI 编码的稳定性税会随着团队规模放大。小团队（5 人）可能感知不到，但 50 人团队会明显感到 bug 率上升、hotfix 增多。在企业级落地时，必须把 DORA 指标的 AI 影响系数纳入研发效能看板，否则就是”开着 AI 这辆车，但没有仪表盘”。
