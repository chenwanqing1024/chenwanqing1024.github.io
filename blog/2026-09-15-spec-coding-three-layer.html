读文笔记：Spec Coding 三层规范体系——约束、示范、视觉

2026-09-15 · AI 编程 Claude Code Spec Coding 规范体系 工程师能力

读文笔记。本文是对他人文章的摘要与评述，非原文转载。 原文：AI编程能力边界探索：基于 Claude Code 的 Spec Coding 项目实战｜得物技术 · 得物技术

原文在说什么

得物技术用 10 天时间，借助 Claude Code 跑完了一个完整企业级中后台（表格、表单、卡片列表、数据看板），交付了 25546 行净增代码、提效 36%。文章的重点不是”AI 能写代码”，而是规范体系的设计——所有数据来自 109 个 .jsonl 会话文件的整体统计。

工具调用分布（2754 次）： AI 自主完成 738 次文件读取、550 次代码编辑、662 次终端命令执行、208 次 TodoWrite 任务进度标记。几乎覆盖了一个研发日常工作的全部动作类型。

三层规范结构（核心）：

  • 第一层 约束层 .claude/rules/： 7 个 md 文件约束 AI 不能做什么。ts.md（禁止 any、使用可选链）、code-names.md（kebab-case/camelCase/PascalCase）、comment.md（JSDoc、@ai-context、@ai-rules 文件头）、lint.md（单引号、文件末尾换行）、style.md（Tailwind CSS、less）、pages.md（constants/services/hooks/components 分层）、service.md（fetch{Name}Api 命名 + UniversalResp<T> 泛型）。
  • 第二层 示范层 .claude/code-design/： 6 个完整模板。pro-table（搜索/分页/批量操作/行操作）、pro-form（创建/编辑双模式 + 字段验证）、editable-pro-table（行内编辑/添加/保存/删除）、drawer（标准打开/关闭逻辑）、compontent（含 README + Props 定义 + 使用示例）、utils。让 AI “参考 pro-table 生成知识治理列表页” 时直接继承整套模式，一次成稿不用多轮调整。
  • 第三层 视觉层 .claude/ui-design/： HTML 设计稿作为视觉锚点（knowledge-spaces.html / search-strategy.html / space-detail.html）。AI 读取 HTML 中的结构和样式信息后，UI 与设计意图吻合度明显高于纯文字描述。

两个 MCP 工具解决信息断层：

  • 接口文档 MCP： AI 按 URL 自动拉取完整接口文档——入参字段、出参结构、枚举值、必填项标注。累计调用 21 次，覆盖 39 个接口。后端未生效时还能同步生成 mock 数据。interface.ts 类型定义质量”无需人工校对”。
  • 飞书云文档 MCP： AI 直接读取飞书云文档内容（PRD、设计说明、技术文档），省去”打开→复制→粘贴”的心智成本。

4 个典型案例：

  1. AI 扮演产品经理： Rules 植入”首席产品专家”Persona，把 AI 从”急于执行”模式切换为”先想清楚”模式；
  2. AI 扮演 UI 设计师： Rules 定义设计规范，对话式生成 HTML 文件作为高保真原型，而非源码；
  3. SDD 驱动”定时任务管理”模块： 6 个接口零联调返工，人工指令 < 10 条，AI 代码占比 100%；同日额外交付两个完整模块，3 个模块单日开发完成，人效提升 3 倍；
  4. 首页重构： 9 组 34 个子任务（grep 确认归属 → 按新分层迁移 → 更新 import → tsc 检查 → 冒烟验证），AI 全程独立执行，人工干预 < 5 条指令。useChat 从 20+ 方法拆为 3 个单职责 hook，ChatInterface 从 17 个 props 缩减至 6-8 个。

AI 失效三模式： 规范真空（AI 自填”合理默认值”）、信息孤岛（看不到会话外状态）、任务目标模糊（把”该问人的问题”当执行问题）。

我的看法

我认同： 文章把”AI 编程”重新定义为”AI 是顶级执行者，人维护确定性空间的边界”。这个比喻很准——AI 极度服从（执行规范不打折扣）、无限耐心（34 个任务不嫌烦）、没有内部业务常识（不知道上周接口换过版本）。理解了”AI 不知道什么”比”AI 能做什么”更重要。前端构建排障那次 4 小时 7 会话就是典型案例：AI 每次分析都正确，问题在于”问题的结构性特征超出了 AI 的信息范围和反馈机制”。

这篇文章给我最有价值的不是三层规范本身，而是”约束层只是规范，不是能力”这个认知。 只有 rules 时，AI 知道”不能用什么”但不知道”该用什么”；加入 code-design 示范层和 ui-design 视觉层后，AI 才有了对齐的锚点。规则是负面清单，模板和设计稿是正面参考，两者缺一不可。这个洞察直接影响了我的项目结构——单纯堆 .cursorrules 不够，必须配上 reference 代码和 design token。

反直觉的工程判断：

  1. CLAUDE.md / rules / code-design 是放项目里的，不是放个人配置里的。 文章把规范放在 .claude/rules/ 和 .claude/code-design/ 下，意味着这些规范跟着项目走、跟着代码一起 review、跟着团队成员复用——而不是某个人的”AI 使用心得”留在 ~/.claude/ 里。这是把 AI 规范纳入工程治理的关键。

  2. HTML 设计稿作为视觉锚点比 PNG/Sketch 文件更有效。 AI 能”读”HTML 里的结构和样式信息（class、布局、间距），但读不了图片里的像素位置。ui-design/*.html 直接在浏览器打开预览，又作为 AI 的视觉参考，一份文件当两份用。

  3. AI 排障的瓶颈不在 AI 的分析能力，在”信息的结构性边界”。 那次 4 小时 7 会话的构建排障，AI 每次分析都正确，问题在于”AI 没有部署环境的真实状态、没有日志、没有历史变更记录”。给 AI 装上 Log MCP / 监控 MCP 比升级 Claude 模型版本更能解决这类问题。

但我有 push back：

  1. “提效 36%”这个数字没给基线。 是和”纯人工开发”比，还是和”AI 辅助但不写 spec”比？和哪个对照组比决定了 36% 是高估还是低估。InfoQ 类文章经常省略对照组，需要警惕。

  2. 三层规范的前期成本没有量化。 写 7 个 rules + 6 个模板 + 4 个 HTML 设计稿，前期投入多少人工小时？如果一次性项目这个投入不划算。文章没说”项目在第几天回本”，意味着读者无法判断什么时候值得这么搞。

  3. 缺少”什么场景 Spec Coding 不适用”的边界讨论。 文章只说了”小颗粒对话框即扫即改、中颗粒 Rules/Skills、中大颗粒 OpenSpec”，但没具体给失败案例——比如”我们尝试用 Spec Coding 做一个 XXX 项目，结果失败了，因为 YYY”。没有反面案例的方法论是不完整的。

怎么落到 Agent 项目

面试被问”如何给 AI 编程搭规范体系”时的回答框架：

  • 约束层（rules）： ts.md / lint.md / service.md 三件套起步，覆盖语法、风格、接口命名；放在 .claude/rules/ 跟项目走，跟着 PR review；不要放个人 ~/.claude/ 里；
  • 示范层（code-design）： 抽出项目里出现 ≥3 次的页面模式（CRUD 列表、表单页、详情页），做成可复用模板；让 AI 用 参考 .claude/code-design/{模板名} 生成 {新页面} 的指令调用；
  • 视觉层（ui-design）： 把 Figma 稿转 HTML，存进 .claude/ui-design/；HTML 既是人类预览源，也是 AI 视觉参考（AI 能读 HTML class/布局/间距，不能读 PNG 像素）；
  • MCP 信息通道： 接口文档 MCP（拉 URL 自动获字段/枚举/必填项）+ 飞书云文档 MCP（直读 PRD）+ 日志/监控 MCP（解决”信息孤岛”失效模式）；
  • 失效兜底： 对”信息孤岛”类问题（部署、监控、日志），专门建 debug Skill 而不是依赖通用 Claude 模型；对”规范真空”场景，强制要求先补 rule 再写代码。

工程落地实践

分阶段里程碑：D1-D2 起草 ts.md/lint.md/service.md 三件套 rules（每条规则带正反例）→ D3-D5 抽 3-5 个页面模板入 .claude/code-design/ → D6-D7 把 Figma 稿转 HTML 入 .claude/ui-design/ → D8+ 接 MCP（接口文档 + 飞书云文档 + 日志）。每个阶段结束都要写”踩坑日志”沉淀进 rules。

关键目录契约：.claude/rules/（强制路径，跟项目走，禁止放 ~/.claude/） + .claude/code-design/（文件名 = 模式名，调用指令 = 参考 {路径} 生成 {新页面}） + .claude/ui-design/（HTML 源，AI 可读 class/布局）。三层目录是规范体系的物理骨架，缺一不可。

常见踩坑 + 兜底：(1) AI 不读 rules → 在 settings.json 里强制 attachRules: true；(2) 模板泛滥 → 每个新模板要求”出现 ≥3 次”才准入；(3) Figma 转 HTML 失真 → 强制保留设计稿原始 layer name，AI 用 layer name 做语义匹配；(4) 规范过期 → rules 文件带 last_reviewed 字段，CI 扫描 90 天未更新自动标 stale；(5) 多人协作覆盖 → rules 进 PR review，冲突按”项目 owner 有最终决定权”。

一句话总结

一句话总结

Spec Coding 的本质不是”AI 写代码”，而是”用三层规范（约束 + 示范 + 视觉）+ MCP 信息通道把不确定性消除在执行之前”——AI 在确定性空间里高速执行，人维护和扩展那个确定性空间的边界。
